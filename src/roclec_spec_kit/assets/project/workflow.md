# Native Roclec workflow — profile 3

Start or resume changes with `roclec-coordinator`. It inspects project state, applies the relevant skills and continues through authorized component integration. Use it for read-only status when asked.

Definition: agreed references → explicit capability/change bundle → exact intent approval → release membership per component → implementation/checks/evidence → integration per component → combined release run → preparation → record existing Git publication.

The project flow, `.roclec/flow.toml`, declares the ten stages (foundation, define, approve, design, plan, implement, verify, review, integrate, release) with each stage's `role`, `ai` (false requires a `reason`), optional `deliverables`, `skills` and `session_evidence`, and the human checkpoints with their `decider`, `criteria` (CR IDs with text under `[criteria]`) and `on_reject` (`revise`, `cancel` or `defer`). The coordinator delegates by `role` and stops at every checkpoint and every `ai = false` stage; approve is always `ai = false`. Foundation, approve and design carry a checkpoint. Implement, integrate and release may carry an optional hook (`pre-implement`, `pre-integrate`, `handoff`); a handoff checkpoint must use `on_reject = "defer"`. The flow is project-owned (seeded once, preserved by refreshes) and is agreed as the reference with role `process`: `reference add flow --path .roclec/flow.toml --role process --component NAME` for every component, then `foundation agree --ref flow ...`. Editing it afterwards blocks the implement gate and the release gate until it is agreed again. `views --write` generates the readable view (default `docs/flow.md`); `check` warns `FLOW_VIEW_STALE`, `FLOW_MISSING` and similar.

Every decision at a declared point takes `--criteria FILE`, the person's own JSON evaluation `[{"id": "CR-001", "status": "met|not-met|n/a", "reason": "..."}]` of exactly the criteria declared for that point (`n/a` needs a reason; an approval has no `not-met`; a rejection of a point that declares criteria cites at least one `not-met`). Commands: `change approve`, `foundation agree`, `checkpoint` and `reject`. Points: `change approve` and `reject change` use `approve`; `foundation agree` and `reject adr|reference` use `foundation`; prototype `checkpoint` and `reject prototype` use `design`; hook checkpoints use their hook. `--consequence` defaults to the point's `on_reject`. Hook checkpoints are `checkpoint CHG-ID --hook pre-implement|pre-integrate|handoff --component NAME --digest DIGEST --outcome approved|rejected --actor ACTOR --reason TEXT --criteria FILE [--run RUN-ID] [--corrections FILE --consequence C --fut FUT-ID]`, with DIGEST the proposal digest, the passed run's candidate `inputs_digest` (with `--run`) or the integration record digest. A declared hook blocks its gates until approved: `pre-implement` the implement, verify and integrate gates; `pre-integrate` the integrate gate and `integrate prepare`; `handoff` the release gate and `release prepare`, all with `CHECKPOINT_REQUIRED`, whose remediation names the exact command. A handoff rejection is only `defer`, with a FUT, and then allows removing that member from the planning release. Neither the gate nor an agent can record these decisions on the person's behalf.

Knowledge skills are the consumer's own references with role `skill` in `.agents/skills/ID/`, distinct from the `roclec-*` skills Roclec refreshes. Register one with `reference add ID --path .agents/skills/ID --role skill --component NAME` and have the user agree it with `foundation agree --ref ID --actor ACTOR --reason TEXT --criteria FILE`; any edit to the folder makes it stale until agreed again. `change approve` pins every skill of the change's components, at any stage, in the decision. Implement requires every skill registered for the component, whatever its stages, agreed on its current bytes (`FOUNDATION_INCOMPLETE`); `inspect --change CHG-ID` lists them per component and stage, and the coordinator gives each role those skills by id and path. `roclec skills` copies them to `.claude/skills/` and regenerates the authority map in the managed block of `AGENTS.md`/`CLAUDE.md`; never edit the copies.

Approve and assign changes on the configured `trunk_ref`. Worktrees on other branches can record a start, a run and evidence. The profile executes configured checks, so verify only repositories you trust. Raw output goes to local runtime logs. Integration requires a fetched target tracking ref that contains the candidate commit.

Read `.roclec/model.md` for JSON authoring. Commands use `roclec --project ROOT --json COMMAND` or `./.roclec/run --json COMMAND`. The launcher always supplies ROOT. Init does not invent contracts or install product policy. `skills` installs/refreshes native instructions; `speckit` installs optional aliases only after the desired spec-kit integration was initialized. Templates/constitutions remain consumer-owned after seeding.

Sources: references.json links agreed existing documents; contracts/<CAP>/<SHA> contains immutable snapshots; current.json alone maps integrated component/capability revisions. Changes contain intent, exact bases, normative deltas and proposed snapshots. Approval freezes that digest. A new semantic revision needs a new approval; integrated participants preserve their original intent and cannot be redefined by pending work. FUT captures discovery, not approval. Each approved change declares its sources, captured Markdown and criterion-to-AC coverage. Capture only necessary source text and redact personal data before sealing. Inspect the change to review mappings and use `list changes --origin ID` to find related changes. ADR references (role `decision`, ID ADR-NNN) have a derived state listed by `list adrs`; only `foundation agree` by the user accepts one, and a later agreed ADR that declares `supersedes` replaces it for new changes. The release gate reports members that applied a since-superseded ADR as `limitations` without blocking.

Use inspect with exactly one selector: `--change CHG-ID`, `--capability CAP-ID`, `--fut FUT-ID`, `--adr ADR-NNN`, or `--release VERSION --component NAME`. Gate approve validates definitions and requires the change's `architecture_decisions` declaration (`ADR_UNDECLARED`) with current pins (`ADR_PIN_STALE`); implement requires approval, foundation, every cited ADR accepted with its pinned content (`ADR_NOT_ACCEPTED`, `ADR_PIN_STALE`), one release assignment for the current intent revision and satisfied dependencies. If an unpublished release still names an older intent, replan it through `release plan` before starting or verifying work; old runs and reviews do not transfer. `run verify CHG-ID --component NAME --base REF --role ROLE --context CONTEXT` executes configured checks, records who produced the run (role implementer, coordinator or human, and the actual session or tool identity as context), retaining immutable logs and interrupted/incomplete attempts. `check --gate verify --change CHG-ID --component NAME` only reads records. Check acceptance_ids mappings and manual evidence must cover applicable ACs. Imported reports never claim native execution.

Review is enabled by default. The profile may set `[review]` values `enabled` and `material_severity`; a change may override the policy through `review policy --change ID --enabled true|false --actor NAME --reason TEXT`. When enabled, a current ready independent report is required for verified/integration/release; tests can still run before it exists. The report declares its role (reviewer or human) and context; a context equal to the run's producer context is rejected as `SELF_REVIEW_DECLARED`, and a run without a recorded producer cannot satisfy review until it is rerun. Each review resolves the open findings in its scope. Findings remain active across candidates; material open findings block verification and integration. Inspect them with `list findings --change ID --open` or `list findings --release VERSION --component NAME`. The user can accept, invalidate or defer a finding with an attributed decision; deferral cites an existing FUT. Real independence, visual quality and sufficient assertions require semantic evaluation.

Integrate with `integrate prepare ID --component NAME --run RUN-ID --out FILE` then `operation apply FILE` for authorized integration. The affected code repo must be clean, committed and completely classified. New/untracked/ignored inputs must not escape the manifest; declare inputs, generated outputs and explicit excluded patterns. Root AGENTS/CLAUDE and installed skills may need explicit classification as inputs. Operational metadata is outside the code fingerprint, but pending metadata in a code repo still blocks the next final gate until committed. Roclec never commits automatically.

Release membership is only in release.json. Normal vX.Y.0 increments X or Y and resets subordinate numbers. Hotfix/bugfix increases only Z and contains fixes from a real published base. Run `run verify --release VERSION --component NAME --base REF --role ROLE --context CONTEXT` after integration to test the final combined contract. Release-scoped observations/review attach to that run; inspect release shows the aggregate policy. `release prepare NAME VERSION --run RUN-ID --out FILE` exports eligibility; operation apply persists it. `release record NAME VERSION --preparation SHA --commit REF --tag VERSION --remote NAME --actor NAME --reason TEXT --out FILE` queries existing remote Git refs; apply records that verified publication. Neither operation creates tags, pushes or deploys.

Export plans outside affected code repos to avoid introducing uncommitted files. Apply reconstructs plans, rechecks preconditions under a local lock and journals writes. On IO_PARTIAL preserve the journal and use operation inspect/recover; recovery refuses divergence and never rolls back later authority. Verify a dead owner before removing a stale empty lock. Repeated apply returns historical receipts without replaying pointers. A local lock is not distributed coordination.

A structured exit-1 workflow issue such as `RELEASE_UNASSIGNED`, `REVIEW_REQUIRED` or `COVERAGE_MISSING` is an observed domain gate, not a crashed tool. An invalid invocation, IO error, timeout or unreadable result is a technical failure. Do not retry either automatically: continue after a domain gate only when the original authorization covers the concrete prerequisite and that prerequisite has actually changed.
