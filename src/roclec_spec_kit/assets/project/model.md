# Native record authoring — model_schema 2, profile 3

All JSON rejects duplicate/unknown keys, non-finite values and escaping/symlink content paths. Lists of IDs/components/references are sorted and unique. CAP/REQ/AC/CHG/FUT use at least three digits. RUN and EVD use ULIDs and explicit supersession. The CLI fills `supersedes` per run scope, per observed AC and per reviewer. Distinct change and release scopes do not share predecessors.

`change seal DIR` computes file hashes, snapshot revisions and the proposal digest. `change seal DIR --check` reports pending changes. Author new proposed snapshots under `proposed/CAP-NNN/draft/` and omit their `revision`; list extra semantic files as keys in `semantic.files`. Seal only an external bundle, then import it with `change new`.

## Change bundle

`change new --file /input/change.json` imports validated content inside that input directory. change.json contains model_schema, id, kind (`evolution|fix|refactor`), semantic and proposal_digest. Semantic contains:

- intention: Markdown path, normally proposal.md; files: {path: exact sha256} of intention/supporting semantic files.
- `origins` contains entries with `kind`, `id`, `locator`, `captured` and `criteria`. The supported kinds are `fut|story|issue|incident|request`. Use an ID unique within the change, a source location, a relative Markdown capture path and sorted, unique criterion IDs. A request also requires `actor`. At least one origin is required for approval. `change seal` adds each captured path to `files` and hashes its bytes. The consumer is responsible for the captured content. Include only needed text and redact personal data before sealing.
- `coverage` contains `criteria` and `derived`. Each criterion entry names `origin` and `criterion` and has exactly one status. Use `covered` with sorted, unique, nonempty `acceptance_ids`, `excluded` with `reason`, `deferred` with an existing FUT ID in `fut`, or draft-only `gap` with `question`. Every origin criterion needs an entry. Each AC that the evolution adds or changes must appear in a covered entry or in `derived` as `{id, reason}` for an obligation added to address a source gap. A covered entry can cite an existing AC that applies to the change. A structural check cannot judge whether the mapping is semantically adequate.
- components: explicit configured names.
- bases: [{capability_id, component, revision}]. Revision null means expected absence; otherwise an exact immutable contract SHA. Each affected pair is explicit.
- deltas: add/retire {op, capability_id, requirement_id}; revise adds retire_acceptance_ids and add_acceptance_ids (optional editorial=true only when behavior truly stays identical); replace uses old_requirement/new_requirement.
- proposed: [{capability_id, components, revision}]; import a complete snapshot under proposed/CAP-NNN/SHA/.
- dependencies: [{component, capability_id, revision}] or [{component, release}]. Empty lists are explicit.
- references: [{id, sha256}] pinned to agreed reference bytes.
- `addresses`: when revising a rejected proposal, use `{ "rejection": "DECISION_SHA", "corrections": [{"id": "R-1", "status": "addressed"}] }` to link the rejection and respond to each correction. Use `disputed` with a `reason` when applicable. Approval checks complete structural coverage, while the user decides whether the responses are sufficient.
- `prototypes`: `[{"path": "docs/prototipo.html", "sha256": "SHA"}]` for the prototypes the change cites. `change seal` pins current project bytes. The implement gate requires an approved checkpoint for the current bytes.
- `sessions`: optional sorted, unique EVD IDs of the agent sessions that drafted the bundle; omit it when empty. Each must be an agent session of this change (`change seal` and `change new` check it).
- architecture_decisions: exactly one of {"adrs": [{id, sha256}]} (non-empty, sorted by ADR ID) or {"none": "reason"}. `change seal` fills a missing sha256 from the current ADR file. Optional while drafting; approval requires it and requires each pin to match the current file. Implement, verify and integrate require every cited ADR to be accepted with the pinned content. An integrated change keeps its pin when the ADR is later edited or superseded.

Evolution has explicit normative deltas. Same obligation retains REQ and gains a new immutable revision; changed behavior needs new ACs. Another obligation uses replace/retire. Fix/refactor has empty deltas/proposed and preserves exact bases. A historical fix adds baseline_release {component, version}. A fix may add fixes [{component, commit, requirement_ids, acceptance_ids, backport}]; commit is an immutable full Git SHA (40 or 64 lowercase hex digits) and must resolve locally at the final gate, and the requirement/AC IDs belong to that exact baseline. Backport is null or {commit}, with optional evidence_id when an exact report is already selected. Preparation checks the included commit and current release-scoped preservation observation, then freezes the resolved evidence ID; no future EVD ID must be guessed during approval. A PR URL or SHA-shaped string alone is insufficient. Capture implementation references before approving the fix; the kernel never guesses them from Git messages.

For an origin of kind `fut`, import the draft first and record its promotion or duplicate relationship to that change before approval. A deferred criterion must cite an existing FUT. Inspect the change for its origins and coverage. `list changes --origin ID` matches the declared ID across all origin kinds and locators. Qualify IDs with the source system when otherwise ambiguous. Existing schema-2 proposals without these fields remain readable. Approval requires both fields.

Approving freezes the imported snapshot and intention under revisions/<proposal_digest>. Editing semantic content creates another digest and requires another explicit approval. For pending participants, preserve completed component obligations; change already integrated behavior with another CHG. Supporting work notes need not become another normative source.

## Contract snapshot

contract.json contains model_schema, capability_id, requirements, acceptance, references and files. Requirements are [{id, statement, components, acceptance_ids}]; statement is a Markdown path. Acceptance entries are [{id, scenario, components}]; scenario is a Markdown path. Files is {each referenced Markdown path: sha256}; texts live only in those files. References are [{id, sha256}]. AC applicability must be a subset of its owner's component applicability. The contract revision resolves its original content forever.

## Foundation and decisions

references.json contains model_schema and references [{id, path, components, role, decision_id}]. Roles are context, principles, architecture, stack, engineering, verification, operations, design, process and skill. Role `decision` registers an architecture decision record (ADR): its ID is ADR-NNN (at least three digits), its path is a Markdown file under the profile's `[adr]` folder (default `docs/adr/`), and it adds `supersedes`, a sorted list of ADR IDs (empty by default; no self, unknown or cyclic entries). Other roles keep lowercase IDs and never carry `supersedes`. An ADR's state is derived, never written: proposed (no agreement), accepted (agreement matches the file bytes and `supersedes`), stale (either changed after the agreement), superseded (another agreed ADR lists it). `foundation agree` on an ADR also records its `supersedes`; `reference update` clears the agreement. ADRs are not part of the foundation roles a component needs, but a registered ADR is a candidate input of each component it names, like any reference: do not list it under excluded or generated; editing it makes pending evidence of those components stale. `check` warns `ADR_STRUCTURE` when an ADR lacks a required `##` section or has fewer than two `###` options under the options section, as configured in `[adr]`. Role `skill` registers a consumer-owned knowledge skill: its canonical path is the folder `.agents/skills/ID/` containing `SKILL.md`, its ID is lowercase and never starts with `roclec-` or `speckit-` (reserved for the procedure skills Roclec installs), and symlinks are rejected. Its fingerprint covers every file of the folder. `inspect --reference` reports a reference as `draft` until agreed, `approved` while its bytes match the agreement, and `stale` when it was agreed and then edited (any file of a skill folder); `foundation agree` again makes it current. After a rejection it can also report `rejected`, `revised` or `withdrawn`. A skill applies to the `components` of its reference and, when a stage lists it in `skills`, only to those stages. `change approve` records `skills: [{id, sha256}]` in the decision, pinning every skill of the change's components at any stage (optional key; absent in earlier decisions); implement requires every skill registered for the component, whatever its stages, agreed on its current bytes (`FOUNDATION_INCOMPLETE`), and `inspect --change` shows per component and stage each skill's id, path, sha256, pinned, drift and state, where drift from the pin does not block. `roclec skills` copies each registered skill byte for byte to `.claude/skills/ID/` (Codex reads `.agents/skills/`); `check` warns `SKILL_COPY_DIVERGED`, `SKILL_UNREGISTERED` and `AGENT_INSTRUCTIONS_STALE` (the authority map in the managed block of `AGENTS.md`/`CLAUDE.md`, regenerated by `roclec skills` and `views --write`). Existing consumer files stay authoritative. Use `reference add|update` and `foundation agree` for decisions bound to source bytes. Each decision has a digest ID and a `previous` link within its entity chain. Change-start decisions have separate chains per change and component. `.roclec/decisions/` holds these approvals and agreements; ADRs are consumer documents registered in references.json. Resolve any decision fork in the merge candidate before advancing trunk.

A FUT record (`fut capture --file FILE`) may declare `scope`: `product` (default when absent) or `process` (friction in the project flow). `foundation agree --ref REF --fut FUT-NNN` (repeatable, process reference only) records the open (captured or evaluating) process FUTs the flow agreement addresses as `futs` in the decision. `fut decide FUT --outcome promoted --target DECISION` may promote a process FUT to a foundation decision only if that decision cites it (other targets such as CHG, CAP or REQ stay allowed), and never promotes a product FUT to a process agreement. A define session may name a CHG ID not imported yet, so the first bundle can cite the session that drafted it; the implement gate re-checks define and foundation sessions under the agreed flow. `inspect --fut` shows `scope` and `addressed_by` [{decision, flow, reason, actor}]: the friction, the flow bytes agreed and why; `list futs` shows each scope.

## Rejections and prototype checkpoints

A human can reject a change proposal, ADR, foundation reference or prototype. `reject` records the subject and exact digest, the real actor, reason, corrections with stable IDs and a consequence. `revise` expects another revision; `cancel` cancels a change or withdraws another subject; `defer` cites an existing FUT. Corrections are required except for `cancel`. The rejected content is frozen under `.roclec` and checked for later edits. To register a revised change, seal and import an external bundle with the same CHG ID while its rejection is awaiting a revision. A revision addressing a rejection identifies its decision and every correction with `addressed` or `disputed`; a dispute requires a reason and a user decision. Use `inspect` and `list rejections --open` to find pending corrections. Decisions are recorded on the configured trunk.

A prototype checkpoint records the real user's decision on the exact artifact bytes. The current bytes must match both the approved proposal pin and an approved checkpoint before implementing a change that cites that prototype. Rejection retains the corrections and consequence in the rejection history. Roclec checks the declaration and digest; the human evaluates the artifact and correction sufficiency.

## Flow and stage checkpoints

`.roclec/flow.toml` (`schema = 1`, optional `view`) is project-owned and holds `[roles.NAME]` (`kind` human|agent), `[criteria.CR-NNN]` (`text`) and `[stages.NAME]` for the ten canonical stages: `description`, `ai`, `reason` (required when `ai = false`), `role`, optional `deliverables` (project-relative paths), `session_evidence` (required|optional), `skills` (IDs of registered references with role `skill`, else `FLOW_SKILL_UNREGISTERED`) and `checkpoint = { decider, criteria, on_reject }`. It is agreed as a reference with role `process` for every component; its agreement pins the exact bytes. `--criteria FILE` is a JSON list `[{id, status, reason}]` with status met|not-met|n/a, exactly the criteria of the decision point. Decisions that carry it record `criteria` and `flow` (the SHA-256 of the flow bytes when decided) on `change approve`, `foundation agree`, `checkpoint` and `reject`; the record keeps the evaluation as made and is never re-evaluated against a later flow.

A stage checkpoint is a `checkpoint` decision with subject type `stage`: `subject` {type, entity CHG-ID, digest}, `hook` (pre-implement|pre-integrate|handoff), `component`, `outcome` (approved|rejected), `actor`, `reason`, `criteria`, `flow`, and `run` only for pre-integrate. A rejection adds `consequence`, `corrections` and `fut` (only for `defer`); the approval and the rejection are the same record, with no separate rejection record or frozen copy. Its chain is `(CHG, "checkpoint:<component>")`, so each hook decision links to the previous one of that change component. An approval counts only for the current subject digest and after the latest `revise` rejection. Declared hooks without such an approval fail with `CHECKPOINT_REQUIRED`. A handoff rejection accepts only `defer`, which allows removing that member from the planning release. The generated flow view starts with a managed-view header with its SHA-256; do not edit it. Its "Flow learning" section counts records (flow revisions and the process FUTs they address, rejections per stage, findings, ai = false stages, sessions per role and stage), so a new record makes `check` warn `FLOW_VIEW_STALE`. `views --write` runs only on the trunk: on a branch the warning stays until the work is merged and the view is regenerated there. `docs/flow-retro.md` is the consumer's retrospective, seeded once and never overwritten.

## Execution/evidence

The profile declares inputs/generated and optional excluded patterns per component. Checks declare id, argv list, cwd, timeout_seconds and optional acceptance_ids and env. Run checks only in repositories you trust. They execute the profile's argv. Raw output is local under `.roclec/runtime/logs/` and may contain secrets. A run manifest binds the captures by path, SHA-256, size and completeness. `run verify` requires `--role` (implementer, coordinator or human) and `--context` (the actual session or tool identity, one line); the run start and manifest record them as producer {role, context}.

Imported evidence contains model_schema, kind (manual|automated-import|independent-review), change_id, component, run_id, candidate_digest, actor, context, outcome, acceptance_ids, checks, limitations and findings. Each finding has id (F-n), severity (blocker|major|minor|info), location ({path, line} or null), acceptance_ids, condition, impact and description. Its stable key is EVD-ID#F-n; optional recurs_from cites a previously fixed finding. Each independent review has resolutions [{finding, status, candidate_digest, note}], resolving all open and still-open findings in scope with fixed or still-open. The reviewed candidate digest and a nonempty note are required. For a release use change_id=null and add release {component, version}; its RUN covers the final combined contracts. Outcome is pass|fail|incomplete for observations or ready|changes-needed|incomplete for independent review. Review adds policy_id and role (reviewer or human). A review context equal to its run's producer context, ignoring case and surrounding whitespace, is rejected as SELF_REVIEW_DECLARED; a run without producer cannot back a review, so rerun `run verify` with --role and --context. Roclec compares declared contexts, not real independence. Current scope/digest must match the actual run. Imported evidence always has executed_by_roclec=false. Files emitted by the CLI are immutable; subsequent observations create new EVDs.

A user decision is imported through `evidence record --file FILE` with model_schema, kind=finding-decision, change_id, component, actor, reason, findings (sorted unique keys), and status (accepted|invalid|deferred). For release scope use change_id=null and release {component, version}. Deferred requires an existing fut_id. Optional severity records a reclassification. Finding state is derived from immutable evidence. Review is enabled by default and the material severity defaults to major; `[review]` in the profile can set enabled and material_severity. An attributed review policy decision can override the default for a change. With review enabled, open material findings block verification and integration. Release gates list open, accepted and deferred findings for members and the release.

An agent session is imported with `evidence record --kind agent-session --file META.json --transcript PATH`; Roclec never parses the host's transcript format. META.json contains model_schema, host, host_session_id, actor, role, model, started_at, ended_at and stage, and must not declare kind. host, host_session_id, actor and model are single-line text; role is a built-in role or an agent role declared in `.roclec/flow.toml`; timestamps are UTC `YYYY-MM-DDTHH:MM:SSZ` with ended_at not before started_at; stage is a flow stage. Scope depends on the stage: foundation requires subject (a registered reference or ADR ID); release requires release {component, version} of a planned release (optional component equal to it); every other stage requires change_id, and component (within the change scope) is required for design, implement, verify, review and integrate and optional otherwise. The original is kept byte for byte under `.roclec/runtime/sessions/EVD-ID/NAME` (local, untracked, owner-only). The record `.roclec/evidence/EVD-ID.json` adds kind=agent-session, id, executed_by_roclec=false, digest and transcript {name, sha256, size, storage, versioned_sha256, redactions}. Optional `[sessions]` in the profile sets `storage` and `quota_bytes` (default 16 MiB). A transcript over the quota is rejected with SESSION_QUOTA_EXCEEDED and nothing is written; it is never truncated. `versioned-redacted` (default) versions `EVD-ID.session` as strict UTF-8 with each `secret_env` value and `redact_patterns` match replaced by `[REDACTED]` and counts the replacements; `versioned-raw` versions an identical copy and `check` warns SESSION_RAW_VERSIONED because it may contain secrets; `local` versions no copy. `check` reports a missing local original as SESSION_RAW_UNAVAILABLE (non-blocking) and an edited original or copy as HASH_MISMATCH. Sessions are not reports: they never cover acceptance criteria, supersede reports or carry findings.

Records cite the sessions that produced them in an optional `sessions` list (sorted, unique EVD IDs, omitted when empty): `--session EVD-ID` (repeatable) on `change approve|cancel|start`, `foundation agree`, `reject`, `checkpoint` and `fut decide`, stored in the decision; on `run verify`, stored as `producer.sessions`; and in manual, automated-import or independent-review evidence JSON. Every cited ID must be an existing agent session in scope: of the same change for change records (bundles, change decisions, hook checkpoints, runs and evidence), of the same release for release runs and evidence, with `subject` equal to the reference for `foundation agree`; other decisions accept any agent session. A bad citation is rejected with INVALID_REFERENCE and nothing is written. With `session_evidence = "required"` on the review stage, an independent review's `context` must be the EVD ID of a `reviewer` session of stage review for the same change and component (SESSION_REQUIRED otherwise); with `optional`, free text stays allowed but an EVD-shaped context must resolve to such a session. The demand applies to change reviews only; a release review keeps free-text context, and an EVD-shaped one must resolve to a `reviewer` session of stage release for that release. A review session cited by its run, or sharing `host_session_id` with a session its run cites (producer context or `producer.sessions`), is SELF_REVIEW_DECLARED. `inspect --change` lists in each flow stage row the `sessions` citing that change and stage (component rows include sessions without a component; foundation rows list sessions whose subject is a reference of the component; release rows sessions of the change's releases).

`session_evidence = "required"` (only on a stage with `ai = true`) makes the gate that closes the stage demand at least one session of that stage and scope, read from the same flow as the gate's checkpoints: foundation at `foundation agree` (subject = reference); define at the approve gate and `change approve`; design (user-facing components) and plan (no component or the gate component) at the implement gate; implement at the verify gate; verify and review (when the change's review is enabled) at the integrate gate; integrate at the release gate for each member on the release component; release at `release record`. Without one the gate fails with SESSION_REQUIRED naming the stage and scope to import. An integrated component is not re-gated for its earlier stages. The seeded flow requires sessions on every AI stage.

## Releases and plans

release.json is the sole membership authority: component/version/kind/base_tag and changes [{change_id, intent_revision}], with model_schema. Plan membership through the CLI. Final release verification covers all current integrated contracts (or the declared historical correction baseline), not superseded criteria from earlier member proposals. Ready requires actual tests/observations and current adopted review.

Prepare/apply creates immutable preparations/<SHA>.json. Record/apply checks an existing local and remote tag against the prepared commit and creates publication.json; publication freezes membership/contracts/candidate/evidence. The remote query is read-only. Metadata-only descendant commits may carry operational records without changing tested inputs; they do not change the prepared shipped commit. No command creates tags, pushes or deploys.
