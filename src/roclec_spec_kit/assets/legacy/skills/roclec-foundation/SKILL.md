# Roclec foundation

## Resolve context

Read the local `AGENTS.md`, `CLAUDE.md` and `.roclec/workflow.md`. Use `./.roclec/run`; from a linked code repo it discovers the specs project through `.roclec/link.toml`. For an existing feature run `./.roclec/run inspect <NNN-or-name> --json`; use its absolute `project` and artifact paths, rather than assuming specs are in the current repo. Explicit input wins over saved context. Without input use `inspect --json`; if no selection exists, ask which spec, never pick the newest folder. Mutating stages run `use <NNN>` to persist selection. Read `.roclec/project.toml` at the resolved project root and the existing constitution (`.specify/memory/constitution.md` if present, otherwise `.roclec/constitution.md`). Report conflicting constitutions instead of silently choosing one.

Run one requested stage per message. Preserve existing IDs, project customizations and human decisions. Status belongs in spec front matter; release membership belongs in version files. Generated roadmap/indexes are never edited. Use `transition` for lifecycle changes and `check --write` after artifact edits. Report files changed, checks, blockers and one next stage; do not run it automatically. An alias invoked through spec-kit follows this same workflow and uses Roclec's CLI, not upstream feature-creation scripts.

## Procedure

Resolve project root from config/link without requiring a selected feature. Read project rules, existing product/design documents and skills-lock.json. Identify the requested user-facing component. Gather actors, problems, constraints, visual/accessibility direction and existing brand decisions; avoid imposing a generic stack or design system. Use pinned project design skills, restoring the lock when required. For public-facing web pages, consider `design-taste-frontend` for art direction while preserving the project's brand and design authority; the skill does not apply to dashboards or app screens. Respect existing product/design source paths and generated-document ownership; if absent propose one canonical source per fact. Document the agreed foundation and check consistency with other components. Run `check --write`; do not draft feature UX or start the next stage automatically.

## Optional generated product context

Read components.<name>.product in project.toml. When adopted, its core/source files own product truth, output is generated by `roclec product --write`, and design names the component design authority. Never edit output by hand. Defaults are product/core.md, product/<component>.md and components/<component>/{PRODUCT,DESIGN}.md. Keep Platform and Stack only in the component source; shared sections combine core first. Run product then check. Without this optional table preserve existing conventions; adoption and migration require a reviewed mapping of existing sources and must not overwrite them.
