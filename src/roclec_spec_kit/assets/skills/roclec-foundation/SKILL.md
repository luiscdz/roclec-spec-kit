# Roclec foundation

<!-- managed by roclec-spec-kit -->

Read project instructions, `.roclec/project.toml` (schema 3), `.roclec/workflow.md` and applicable agreed references. Use `./.roclec/run --json ...` or `roclec --project ROOT --json ...`; the launcher supplies the project root. Select explicit CHG/CAP/FUT/release and component for mutations. Inspect with `inspect --change CHG-001`, `inspect --capability CAP-001`, or `inspect --release vX.Y.0 --component NAME`; never guess from branches or the newest folder.

Preserve consumer-owned templates, identities, decisions and immutable history. Contracts live in snapshots and current.json; release.json alone owns membership. Status is derived, never an editable done field. Read `.roclec/model.md` when authoring JSON. Passing structural checks does not establish semantic sufficiency or user approval. Complete the authorized scope; ask only for unresolved material decisions. Report actual evidence, limitations and one useful next action without executing an unauthorized action.

Inventory existing context, principles, architecture/stack, engineering, verification, operations and applicable design authorities. Map existing documents rather than creating duplicate truths. Distinguish proposals, agreements and unresolved decisions, with actor/reason and source hashes. Register sources with `reference add ID --path PATH --component NAME --role ROLE` or `reference update`. Record an actual agreement with `foundation agree --ref ID --actor ACTOR --reason REASON --criteria FILE` (the user's per-criterion evaluation of the foundation point of the flow; see the coordinator). For user-facing design consult consumer-pinned design skills when relevant; restore only an existing consumer skills-lock.json when authorized, without guessing a stack. Run `foundation check --component NAME [--change CHG-ID]`. A passing existence/hash check does not certify semantic sufficiency; resolve material gaps before implementation.

Inventory existing architecture decisions too. Register each ADR file under the profile's `[adr]` folder (default `docs/adr/`) as it is, with `reference add ADR-NNN --path PATH --component NAME --role decision [--supersedes ADR-MMM]`; do not rewrite it into the template. An ADR's state (proposed, accepted, stale, superseded) is derived: read it with `list adrs` or `inspect --adr ADR-NNN`. Only `foundation agree --ref ADR-NNN` with the user's real actor and criteria evaluation accepts one, and only after the user decided it. ADRs are not foundation roles that every component needs, and they are not `.roclec/decisions/`, which holds approvals and agreements.

Seed or adapt the project flow with the user: `.roclec/flow.toml` is project-owned (seeded by `init`/`skills`, preserved by refreshes) and holds roles (`[roles.NAME] kind = human|agent`), criteria (`[criteria.CR-NNN] text`) and the ten stages with `ai` (false requires `reason`), `role`, optional `deliverables`, `session_evidence`, `skills` and `checkpoint = { decider, criteria, on_reject }`. Ask which stages the user decides themselves, who the deciders are, which criteria they judge by and whether to add the optional hooks (implement = pre-implement, integrate = pre-integrate, release = handoff; a handoff checkpoint must use `on_reject = "defer"`). Foundation, approve and design always carry a checkpoint and approve is always `ai = false`. Do not invent criteria; propose wording and let the user decide. Run `views --write` to generate the readable view and `check` to confirm no `FLOW_*` warning. Register the flow as the `process` reference for every component: `reference add flow --path .roclec/flow.toml --role process --component NAME`, then ask the user to agree with the exact points' criteria: `foundation agree --ref flow --actor ACTOR --reason TEXT --criteria FILE`, where FILE is the user's own evaluation `[{"id": "CR-001", "status": "met"}]`. Editing the flow afterwards needs a new agreement before implement or release: cite the open process FUTs it addresses with `foundation agree --ref flow ... --fut FUT-NNN` (repeatable), record the foundation session (see `roclec-coordinator`), run `views --write` to refresh the flow view and its "Flow learning", and point the user to `docs/flow-retro.md` for their own reflection. Promote an addressed FUT with `fut decide FUT --outcome promoted --target DECISION_ID`.

Knowledge skills are the project's own reusable knowledge for agents, owned by the consumer; procedure skills `roclec-*` are owned by Roclec and refreshed by `roclec skills`. A knowledge skill is a reference with role `skill` whose canonical folder is `.agents/skills/ID/` with a `SKILL.md`; the ID is lowercase and never starts with `roclec-` or `speckit-`. Inventory the project's own skills: folders under `.agents/skills/` and `.claude/skills/` that are not `roclec-*` or `speckit-*`, and every `SKILL_UNREGISTERED` warning from `check` (an own skill neither registered nor in `skills-lock.json`). Propose registering each one; move one found only under `.claude/skills/` to `.agents/skills/ID/` first, because the `.claude/skills/` copy is generated and never the source. Register it with `reference add ID --path .agents/skills/ID --role skill --component NAME` (repeat `--component` for every component it applies to) and ask the user to agree it with `foundation agree --ref ID --actor ACTOR --reason REASON --criteria FILE`. The agreement pins every file of the folder: any edit makes it `stale` until agreed again, and symlinks are rejected. To capture new knowledge offer `.roclec/templates/skill-template.md` (Purpose, Applies to, Authority, Conventions or procedure, Examples, Verification); the skill cites the references and ADRs it applies under Authority and does not restate them. To limit a skill to stages, list it in `skills = ["ID"]` of those stages in `.roclec/flow.toml` (each must be a registered skill reference, else `FLOW_SKILL_UNREGISTERED`); a skill no stage lists applies to every stage of its components. After registering or agreeing, run `roclec skills` (or `views --write`) so the authority map in the managed block of `AGENTS.md`/`CLAUDE.md` and the `.claude/skills/` copies are current; `check` warns `AGENT_INSTRUCTIONS_STALE`, `SKILL_COPY_DIVERGED` and `SKILL_UNREGISTERED`. Never edit the `.claude/skills/` copy: refresh refuses an edited copy with `MANAGED_FILE_EDITED`.
