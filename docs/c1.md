# Uso del núcleo C1

**Referencia del alcance C1, 0.8.0 local, perfil 2.** Estos comandos siguen disponibles. Las menciones a operaciones futuras describen el límite histórico de C1. Ver [C2](c2.md) para evidencia/integración y [C3](c3.md) para cierre Git e instalación nativa implementados.

## Perfil e inicialización

Adaptar [profile.toml](examples/c1/profile.toml). Los nombres de componentes son del consumidor; dos pueden compartir repositorio. `inputs`, `generated` y `verification` son explícitos. Los checks usan `argv`, `cwd` relativo al repo y timeout, sin shell. C1 valida su forma; aún no los ejecuta.

```bash
roclec --json init /ruta/al/consumidor --profile /ruta/al/perfil.toml
roclec --project /ruta/al/consumidor --json check
```

Se crean perfil, índice vigente vacío, índice de referencias vacío y registro permanente de identidades. Los recibos quedan en `.roclec/receipts`; el runtime local se ignora en Git. No se crean contratos, releases, fundaciones aprobadas ni carpetas de progreso ficticio. Se preservan archivos propios; un destino de inicialización existente provoca rechazo antes de modificarlo.

## Preparar y aprobar intención

Prepara snapshots sin huellas en `proposed/CAP-ID/draft/` dentro del bundle. Ejecuta `change seal DIR` para calcular los hashes, las revisiones y el digest de propuesta antes de importar. `change seal DIR --check` anticipa los cambios sin escribir.

`change new --file` recibe un directorio con `change.json`, `proposal.md` y `proposed/<CAP>/<revisión>/contract.json` más su Markdown. El [ejemplo inicial](examples/c1/change/change.json) es importable en un consumidor vacío con componente `app`; el núcleo no conoce ese nombre. Bases null declaran ausencia esperada; bases SHA, un contrato exacto.

```bash
roclec --project ROOT --json change new --file /ruta/al/borrador/change.json
roclec --project ROOT --json inspect --change CHG-001
roclec --project ROOT --json check --change CHG-001 --gate approve
roclec --project ROOT --json change approve CHG-001 --digest SHA --actor "Responsable" --reason "Decisión explícita sobre este alcance"
```

SHA es `data.change.proposal_digest` de inspect. El gate approve comprueba estructura/base; la decisión semántica la registra la persona responsable con el comando explícito. Se congela intención/contenido/contratos propuestos bajo `revisions/<digest>`. No avanza el contrato vigente ni publica nada.

Editar un borrador requiere modificar su contenido/descriptor y recalcular huellas según [las interfaces](definition/interfaces-primer-corte.md). Los agentes podrán hacer esos pasos mecánicos; aún no se instalan skills nuevas. Un contenido que no coincide con su hash se rechaza. Una edición semántica válida cambia el digest, vuelve a draft y conserva aprobaciones anteriores. Al aprobar se reservan sus IDs nuevos. Notas administrativas fuera de `semantic.files` no cambian el digest. No editar snapshots aprobados ni integrados.

Los deltas add/revise/replace/retire explican todos los cambios aplicables. `revise` declara AC retirados/agregados de esa obligación. `editorial: true` clasifica explícitamente redacción que preserva conducta; es una declaración revisable, no prueba automática de equivalencia semántica. Fix/refactor preservan el contrato normativo.

## Fundación e inicio por componente

Registra cada fuente con `reference add ID --path PATH --component COMPONENT --role ROLE`. Para cambiar sus metadatos, usa `reference update` con los mismos argumentos. Registra el acuerdo con `foundation agree --ref ID --actor ACTOR --reason REASON` y comprueba la fundación con `foundation check --component COMPONENT`.

`.roclec/references.json` tiene `model_schema: 1` y `references: [...]`. Cada entrada declara `id`, `path`, `components`, `role`, `decision_id`. Roles: context, principles, architecture, stack, engineering, verification, operations, design. Se reutilizan documentos existentes; varios roles pueden apuntar al mismo archivo.

Una decisión de fundación es un archivo propio `.roclec/decisions/<id>.json`: `model_schema`, `id`, `kind: "foundation"`, `status: "agreed"`, `actor`, `reason`, `sources` (mapa id de referencia → SHA-256 de sus bytes). Se registra después de una decisión real. Si la fuente cambia, su acuerdo deja de habilitar el inicio hasta revisarlo; conservar un estado agreed sobre contenido distinto no basta.

Antes de implementar se necesitan contexto, principios, arquitectura, stack, ingeniería y verificación acordados, checks declarados y diseño si hay UI. Operación se completa según el hito de entrega. La calidad/suficiencia de los documentos requiere juicio humano; existencia/hash no la certifican.

```bash
roclec --project ROOT --json foundation check --component COMPONENT --change CHG-001
roclec --project ROOT --json release plan COMPONENT v0.1.0 --change CHG-001
roclec --project ROOT --json check --change CHG-001 --component COMPONENT --gate implement
roclec --project ROOT --json change start CHG-001 --component COMPONENT --actor "Responsable"
```

Se exige aprobación vigente, fundación, una asignación de release de la revisión aprobada y dependencias satisfechas. C1 registra inicio, no terminación. Cancelar conserva historia; lo integrado requiere reversión mediante otro cambio. Quitar una asignación iniciada exige cancelar primero ese trabajo pendiente. Tras aprobar una nueva revisión del mismo cambio, se puede volver a planificar explícitamente esa revisión y registrar su nuevo inicio; el historial anterior se conserva.

## Releases y FUT

`release plan` reemplaza explícitamente pertenencia de una versión planning; repetir `--change` para todos sus miembros. `--clear` vacía la planificación, sin borrar historia ni desbloquear contenido publicado. Pertenencias viven solo en `release.json`. Correcciones necesitan base registrada como publicada y tag Git real que resuelva al commit registrado; C1 lee ese historial, aún no lo crea. No se crean ni empujan tags.

```bash
roclec --project ROOT --json fut capture --file descubrimiento.json
roclec --project ROOT --json fut decide FUT-001 --outcome evaluating --actor "Responsable" --reason "Investigar impacto"
roclec --project ROOT --json fut decide FUT-001 --outcome promoted --target CHG-001 --actor "Responsable" --reason "Destino acordado"
```

FUT declara `model_schema`, `id`, `source: {location, locator}`, `finding`, `impact`, `questions`. Promoción exige CAP/REQ/CHG o decisión de fundación existente; no aprueba su destino. duplicate apunta a otro FUT sin ciclos. Reevaluar un hallazgo resuelto exige nueva decisión evaluating y conserva las anteriores.

## Consulta y recuperación

`status` resume los cambios, gates pendientes, ejecuciones sin finalizar y releases en planificación por componente. `list changes|futs|releases|runs` consulta cada colección. Usa `--json` para automatización y `--debug` para obtener la traza de un error interno.

`inspect --capability CAP-001` muestra el vector por componente. `--component NAME --at VERSION` resuelve el contrato histórico de una publicación registrada. `views --write` genera vistas; una edición manual no resuelta bloquea sobrescritura. Proponer cambios no retira AC del contrato integrado.

Las mutaciones validan antes de escribir, vuelven a comprobar precondiciones bajo lock y dejan recibo. Los diarios de C1 son internos, no planes externos ejecutables. Ante exit 4/IO_PARTIAL conservar los archivos y ejecutar `operation inspect ID` y `operation recover ID` con `--project` en la raíz exacta. Recovery funciona aun si falta parte de la inicialización. Una divergencia posterior bloquea recuperación; repetir una ya completada no repite efectos.

El lock local no coordina máquinas/worktrees remotos. Si un proceso muere dejando `.roclec/runtime/lock`, verificar que no sigue activo antes de retirar el directorio vacío del lock y recuperar su journal. No borrar diarios para ocultar fallos. Los gates finales limpios de D2 llegarán con C2; no se realizan commits automáticos.

Un exit 0 de C1 acredita la operación de definición solicitada, no verificación del código, integración ni publicación. Los códigos y sobre JSON están en las interfaces.
