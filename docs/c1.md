# Uso del núcleo C1

Guía de autoría y consultas para el perfil 3 y el modelo 2. [Verificación e integración](c2.md) · [Cierre Git e instalación](c3.md)

## Perfil e inicialización

Adapta el perfil de ejemplo a los componentes y referencias Git del consumidor. Dos componentes pueden compartir repositorio. Declara entradas, archivos generados y comandos de verificación explícitos. [Perfil de ejemplo](examples/c1/profile.toml)

```bash
git init -b main /ruta/al/consumidor
roclec --json init /ruta/al/consumidor --profile /ruta/al/perfil.toml
roclec --project /ruta/al/consumidor --json check
```

Se crean perfil, índice vigente vacío, índice de referencias vacío y registro permanente de identidades. Los recibos quedan en `.roclec/receipts`; el runtime local se ignora en Git. No se crean contratos, releases, fundaciones aprobadas ni carpetas de progreso ficticio. Se preservan archivos propios; un destino de inicialización existente provoca rechazo antes de modificarlo.

## Preparar y aprobar intención

Prepara snapshots sin huellas en `proposed/CAP-ID/draft/` dentro del bundle. Ejecuta `change seal DIR` para calcular los hashes, las revisiones y el digest de propuesta antes de importar. `change seal DIR --check` anticipa los cambios sin escribir.

`change new --file` recibe un directorio con `change.json`, `proposal.md`, las capturas Markdown de los orígenes y `proposed/<CAP>/<revisión>/contract.json` más su Markdown. El [ejemplo inicial](examples/c1/change/change.json) es importable en un consumidor vacío con componente `app` y contiene origen y cobertura. Bases null declaran ausencia esperada; bases SHA, un contrato exacto.

Cada `semantic.origins` declara `kind` (`fut`, `story`, `issue`, `incident` o `request`), `id`, `locator`, `captured` y `criteria` con IDs estables. Un pedido del chat usa `request` y agrega `actor`. El origen puede repetirse en otros cambios y un cambio puede tener varios orígenes. Captura únicamente el texto necesario y redacta datos personales antes de sellar. El consumidor responde por el contenido de esas copias. `change seal` las incorpora a `semantic.files` y calcula sus hashes.

`semantic.coverage.criteria` registra cada par `origin`/`criterion` como `covered` con `acceptance_ids`, `excluded` con `reason`, `deferred` con `fut` existente o `gap` con `question` durante el borrador. Cada AC que la evolución incorpora o modifica debe estar vinculado a un criterio cubierto o declarado en `coverage.derived` con su ID y el motivo por el que la spec lo agregó. Un criterio cubierto también puede vincularse a un AC existente que aplique al cambio. El gate verifica la estructura, mientras que la persona responsable evalúa la coherencia y decide exclusiones y diferimientos. Los campos y formatos completos están en `.roclec/model.md`.

```bash
roclec --project ROOT --json change new --file /ruta/al/borrador/change.json
roclec --project ROOT --json inspect --change CHG-001
roclec --project ROOT --json check --change CHG-001 --gate approve
roclec --project ROOT --json change approve CHG-001 --digest SHA --actor "Responsable" --reason "Decisión explícita sobre este alcance"
```

SHA es `data.change.proposal_digest` de inspect. El gate approve comprueba estructura/base, origen y cobertura sin gaps, y la declaración `architecture_decisions` ([ADR](#decisiones-de-arquitectura-adr)); la decisión semántica la registra la persona responsable con el comando explícito. Se congela intención/contenido/contratos propuestos bajo `revisions/<digest>`. No avanza el contrato vigente ni publica nada.

Editar un borrador requiere modificar su contenido/descriptor y recalcular huellas según [las interfaces](definition/interfaces-primer-corte.md). Los agentes podrán hacer esos pasos mecánicos; aún no se instalan skills nuevas. Un contenido que no coincide con su hash se rechaza. Una edición semántica válida cambia el digest, vuelve a draft y conserva aprobaciones anteriores. Al aprobar se reservan sus IDs nuevos. Notas administrativas fuera de `semantic.files` no cambian el digest. No editar snapshots aprobados ni integrados.

Los deltas add/revise/replace/retire explican todos los cambios aplicables. `revise` declara AC retirados/agregados de esa obligación. `editorial: true` clasifica explícitamente redacción que preserva conducta; es una declaración revisable, no prueba automática de equivalencia semántica. Fix/refactor preservan el contrato normativo.

## Fundación e inicio por componente

Registra cada fuente con `reference add ID --path PATH --component COMPONENT --role ROLE`. Para cambiar sus metadatos, usa `reference update` con los mismos argumentos. Registra el acuerdo con `foundation agree --ref ID --actor ACTOR --reason REASON` y comprueba la fundación con `foundation check --component COMPONENT`.

`.roclec/references.json` tiene `model_schema: 2` y `references: [...]`. Cada entrada declara `id`, `path`, `components`, `role`, `decision_id`. Los roles son context, principles, architecture, stack, engineering, verification, operations, design, process y skill. Varios roles pueden apuntar al mismo archivo.

Una decisión de fundación es un archivo propio `.roclec/decisions/<id>.json`: `model_schema`, `id`, `kind: "foundation"`, `status: "agreed"`, `actor`, `reason`, `sources` (mapa id de referencia → SHA-256 de sus bytes). Se registra después de una decisión real. Si la fuente cambia, su acuerdo deja de habilitar el inicio hasta revisarlo; conservar un estado agreed sobre contenido distinto no basta.

Antes de implementar se necesitan contexto, principios, arquitectura, stack, ingeniería y verificación acordados, checks declarados y diseño si hay UI. Operación se completa según el hito de entrega. La calidad/suficiencia de los documentos requiere juicio humano; existencia/hash no la certifican.

```bash
roclec --project ROOT --json foundation check --component COMPONENT --change CHG-001
roclec --project ROOT --json release plan COMPONENT v0.1.0 --change CHG-001
roclec --project ROOT --json check --change CHG-001 --component COMPONENT --gate implement
roclec --project ROOT --json change start CHG-001 --component COMPONENT --actor "Responsable"
```

Se exige aprobación vigente, fundación, una asignación de release de la revisión aprobada y dependencias satisfechas. C1 registra inicio, no terminación. Cancelar conserva historia; lo integrado requiere reversión mediante otro cambio. Quitar una asignación iniciada exige cancelar primero ese trabajo pendiente. Tras aprobar una nueva revisión del mismo cambio, se puede volver a planificar explícitamente esa revisión y registrar su nuevo inicio; el historial anterior se conserva.

## Decisiones de arquitectura (ADR)

Un ADR registra una decisión que afecta a más de un cambio o componente, es costosa de revertir o tiene alternativas reales con consecuencias materiales. Las demás decisiones siguen en «Decisions and alternatives» del plan. Es un Markdown propio del consumidor en la carpeta `[adr]` del perfil (por defecto `docs/adr/`), escrito desde `.roclec/templates/adr-template.md`, con ID `ADR-NNN`.

```bash
roclec --project ROOT --json reference add ADR-001 --path docs/adr/ADR-001-almacenamiento.md --component app --role decision
roclec --project ROOT --json foundation agree --ref ADR-001 --actor "Responsable" --reason "Decisión acordada"
roclec --project ROOT --json reference add ADR-002 --path docs/adr/ADR-002-cola.md --component app --role decision --supersedes ADR-001
roclec --project ROOT --json inspect --adr ADR-001
roclec --project ROOT --json list adrs
```

El estado no se escribe; se deriva:

| Estado | Condición |
| --- | --- |
| `proposed` | Registrado sin acuerdo |
| `accepted` | El acuerdo coincide con los bytes del archivo y con su `supersedes` |
| `stale` | El archivo o su `supersedes` cambió después del acuerdo |
| `superseded` | Otro ADR acordado lo incluye en su `supersedes` |

Registrar, actualizar y acordar un ADR son operaciones de la troncal. `reference update` reemplaza la entrada y borra su acuerdo. `check` rechaza sustituciones a ADR inexistentes, a sí mismo o en ciclo, y avisa con `ADR_STRUCTURE` si falta una sección obligatoria o hay menos de dos opciones `###` en la sección de opciones. Si adaptas la plantilla, ajusta `required_sections` y `options_section` en `[adr]` ([perfil de ejemplo](examples/c1/profile.toml)). La comprobación es estructural: no certifica la calidad de la decisión.

Cada cambio declara en su semántica `architecture_decisions`: `{"adrs": [{"id": "ADR-001"}]}`, cuya huella completa `change seal`, o `{"none": "motivo"}`. Aprobar sin declaración se rechaza con `ADR_UNDECLARED`, y con una huella distinta del archivo vigente, con `ADR_PIN_STALE`. Se puede aprobar citando un ADR `proposed`, pero `check --gate implement`, `change start`, la verificación y la integración exigen que cada ADR citado esté `accepted` con el contenido fijado (`ADR_NOT_ACCEPTED` o `ADR_PIN_STALE`). Un cambio integrado conserva la huella del ADR que aplicó aunque después se edite o se sustituya; los cambios nuevos citan el reemplazo, y el gate de release informa esos miembros en `limitations` sin bloquear.

Un ADR registrado forma parte del candidato de cada componente que declara, como las demás referencias: no lo listes en `excluded` ni `generated`, y editarlo deja desactualizada la evidencia de los cambios aún no integrados de esos componentes.

`inspect --change` muestra los ADR del cambio con su estado; `inspect --adr` muestra estado, cadena de sustitución y cambios que lo citan. Los ADR no son roles de fundación obligatorios ni se confunden con `.roclec/decisions/`, que guarda aprobaciones y acuerdos.

## Skills de conocimiento

Hay dos tipos de skill. Las skills de procedimiento (`roclec-*`) son de Roclec: `roclec skills` las instala y las refresca. Las skills de conocimiento son del consumidor: convenciones, patrones o procedimientos propios del proyecto que los roles aplican en las etapas del flujo. Las dependencias externas de `skills-lock.json` no cambian y, además, pueden registrarse como conocimiento desde su carpeta canónica `.agents/skills/ID/` (una ruta en `.claude/skills/` se rechaza con `INVALID_PATH`).

Para registrar una, crea `.agents/skills/ID/SKILL.md` (puedes partir de `.roclec/templates/skill-template.md`, que `roclec skills` siembra una vez y los refrescos preservan) y regístrala como referencia con rol `skill`:

```bash
roclec --project ROOT --json reference add convenciones --path .agents/skills/convenciones --role skill --component app
roclec --project ROOT --json foundation agree --ref convenciones --actor "Responsable" --reason "Convenciones revisadas" --criteria criterios.json
roclec --project ROOT --json inspect --reference convenciones
```

- **Ubicación e ID.** La ruta canónica es la carpeta `.agents/skills/ID/` con un `SKILL.md` no vacío. El ID va en minúsculas y no puede empezar por `roclec-` ni `speckit-`. Los enlaces simbólicos dentro de la carpeta se rechazan (`INVALID_PATH`).
- **Huella.** Es un manifiesto de todos los archivos de la carpeta, incluidos los ocultos: editar, agregar, quitar o renombrar cualquiera la cambia.
- **Estados.** `inspect --reference` muestra `draft` (sin acuerdo), `approved` (el acuerdo coincide con los bytes actuales) o `stale`, además de `rejected`, `revised` o `withdrawn` tras un [rechazo](#rechazos-y-prototipos). Desde 0.9.0 `stale` se aplica a cualquier referencia acordada y luego editada; `foundation agree` de nuevo la deja vigente.

### Asignación a componentes y etapas

Una skill aplica a los `components` de su referencia. Para limitarla a ciertas etapas, `[stages.NAME]` en `.roclec/flow.toml` admite `skills = ["convenciones"]`: cada nombre debe ser una referencia registrada con rol `skill`, y si no, `check` falla con `FLOW_SKILL_UNREGISTERED`. Una skill que ninguna etapa lista aplica en todas. Tras editar el flujo hay que acordarlo de nuevo (`foundation agree --ref flow`).

### Fijación en la aprobación

`change approve` registra en la decisión `skills: [{id, sha256}]` con todas las skills de los componentes del cambio, sea cual sea su etapa, y la huella que tenían. Para implementar, cada skill registrada para el componente, aunque el flujo la limite a otras etapas, debe estar acordada sobre sus bytes actuales; si no, el gate falla con `FOUNDATION_INCOMPLETE`. Volver a ejecutar `foundation agree` la desbloquea. La aprobación conserva su fijación original. Si el flujo exige sesiones en `foundation`, cada skill aplicable necesita además su sesión de agente, como cualquier referencia.

`inspect --change CHG-001` agrega la sección `skills`: por componente, etapa e ID, la ruta, la huella actual (`sha256`), la fijada (`pinned`), si hay desviación (`drift`) y el `state`. La desviación respecto de la fijación se muestra pero no bloquea; bloquea el estado `stale`. El CLI ordena las claves del JSON alfabéticamente; en la vista del flujo las etapas siguen el orden del flujo.

### Copias para los hosts

`roclec skills` copia cada skill registrada, byte a byte, a `.claude/skills/ID/`; Codex lee `.agents/skills/` directamente. Solo la instalación en la raíz del proyecto copia: los repos enlazados (`--into`) reciben un puntero al mapa de autoridad de la raíz. Edita únicamente la carpeta canónica.

- `check` avisa `SKILL_COPY_DIVERGED` cuando una copia difiere de la canónica o falta y `SKILL_UNREGISTERED` cuando hay una skill propia en `.agents/skills/` o `.claude/skills/` que no está registrada (con `SKILL.md`). No se avisa para `roclec-*`, `speckit-*` ni las entradas de `skills-lock.json`.
- Un refresco que encuentra una copia editada se rechaza completo con `MANAGED_FILE_EDITED`: restáurala o bórrala. Si el archivo de la copia nunca lo escribió Roclec (no está en `installation.json`) y difiere, el rechazo es `UNMANAGED_FILE`: saca ese contenido de la ruta o bórralo. Si se da de baja una skill, sus copias quedan en disco y `check` las reporta.
- Para los candidatos de verificación, los archivos de la skill son entradas de referencia de sus componentes y las copias de `.claude/skills/` son operativas.

### Mapa de autoridad

El bloque administrado de `AGENTS.md` y `CLAUDE.md` termina con un mapa de autoridad: solo enlaces, agrupados por rol, con las referencias, los ADR y las skills que tienen un acuerdo en `references.json`. Los ADR sustituidos (superseded) se omiten. `roclec skills` y `roclec views --write` lo regeneran; `check` avisa `AGENT_INSTRUCTIONS_STALE` cuando difiere. El texto del consumidor fuera del bloque se conserva byte a byte, y un bloque con marcadores mal formados se rechaza con `UNMANAGED_FILE` hasta corregirlo. Si el flujo es inválido, el mapa lista cada skill en todas las etapas.

## Rechazos y prototipos

Una persona puede rechazar una propuesta de cambio, ADR, referencia o prototipo. El coordinador presenta el sujeto y su huella exacta y registra la decisión con el actor real, el motivo, las correcciones solicitadas y su consecuencia. Las operaciones se registran en la troncal. El contenido rechazado se conserva bajo `.roclec` y `check` detecta ediciones de esa copia.

Un archivo de correcciones contiene una lista como `[{"id":"R-1","description":"Aclarar la recuperación"}]`. La consecuencia `revise` espera una revisión, `cancel` cancela el cambio o retira los demás sujetos, y `defer` exige un FUT existente con el trabajo pendiente. Las correcciones son obligatorias salvo con `cancel`. Para un sujeto retirado se necesita otro ID o ruta para una nueva propuesta.

```bash
roclec --project ROOT --json reject change CHG-001 --digest SHA --actor "Responsable" --reason "La recuperación necesita precisión" --consequence revise --corrections correcciones.json
roclec --project ROOT --json list rejections --open
roclec --project ROOT --json inspect --change CHG-001
```

Prepara la revisión en un bundle externo con el mismo ID. Ejecuta `change seal DIR` y `change new --file DIR/change.json` para registrar la revisión y después presenta su digest para aprobación. `semantic.addresses` enlaza el ID de la decisión de rechazo y cada corrección como `addressed` o `disputed`, con motivo obligatorio si se disputa. El acuerdo de una referencia o ADR usa `foundation agree --ref ID --actor ACTOR --reason REASON --addresses respuestas.json`. La misma declaración acompaña la decisión posterior de un prototipo. Si el usuario vuelve a rechazar un ADR, referencia o prototipo revisado, pasa las respuestas del autor con `--addresses` al registrar el nuevo rechazo. Conserva el archivo de respuestas al último rechazo `revise` para incluirlo también en los acuerdos o checkpoints posteriores. Por ejemplo, `{"rejection":"DECISION_SHA","corrections":[{"id":"R-1","status":"addressed"}]}` responde a una corrección. La comprobación exige cobertura de las correcciones y su forma válida, mientras la persona decide si la respuesta resuelve su pedido. Se deben presentar las correcciones disputadas para su decisión.

Para un prototipo, agrega su ruta a `semantic.prototypes` y ejecuta `change seal` para fijar la huella. Presenta el artefacto real antes de registrar su aprobación explícita con `checkpoint` y el actor real. El gate de implementación exige que los bytes vigentes coincidan con la huella de la propuesta aprobada y con la del checkpoint aprobado. Si la persona rechaza una propuesta ya aprobada para revisar el prototipo, registra su decisión con `--consequence revise`. En el bundle de revisión, quita la huella del prototipo para que `change seal` la complete y responde a las correcciones. Importa la revisión y presenta ambos digests para que la persona apruebe la propuesta y decida sobre el prototipo revisado. Si el cambio ya está integrado, abre otro CHG.

```bash
roclec --project ROOT --json inspect --prototype docs/prototipo.html
roclec --project ROOT --json checkpoint docs/prototipo.html --digest SHA --actor "Responsable" --reason "Diseño revisado" --outcome approved
roclec --project ROOT --json inspect --reference arquitectura
```

`inspect --adr`, `inspect --reference` e `inspect --prototype` muestran la historia aplicable. Para rechazar un prototipo, usa `checkpoint` con `--outcome rejected`, la consecuencia y las correcciones aplicables. El digest SHA identifica la versión revisada. Los criterios de cada punto de control los define el [flujo declarado](#el-flujo-declarado).

## El flujo declarado

`.roclec/flow.toml` es un archivo propio del proyecto. `roclec skills` lo siembra una vez y los refrescos lo preservan. Declara las diez etapas canónicas, en orden fijo: foundation, define, approve, design, plan, implement, verify, review, integrate y release. El [flujo por defecto](flujo-roclec.md#flujo-por-defecto) se genera a partir del archivo sembrado.

Cada `[stages.NAME]` declara:

- `description` y `ai`. Con `ai = false` se exige `reason`; approve siempre es `ai = false`.
- `role`: un rol de Roclec o un rol de `[roles.NAME]` con `kind` `human` o `agent`. Un rol `agent` propio necesita un archivo de enlace con el host (`.claude/agents/NAME.md` o `.codex/agents/NAME.toml`).
- Opcionales: `deliverables` (rutas del proyecto), `session_evidence` (`required` o `optional`; `required` solo con `ai = true` y [exige sesiones de agente](c2.md#sesiones-de-agente-como-evidencia) en el gate de la etapa) y `skills` (IDs de referencias con rol `skill` que aplican en la etapa; ver [Skills de conocimiento](#skills-de-conocimiento)).
- `checkpoint = { decider, criteria, on_reject }`, con `on_reject` en `revise`, `cancel` o `defer`. Los criterios son IDs `CR-NNN` definidos con su texto en `[criteria.CR-NNN]`.

Foundation, approve y design tienen punto de control obligatorio. Implement, integrate y release admiten uno opcional (ganchos `pre-implement`, `pre-integrate` y `handoff`), y el de release solo admite `on_reject = "defer"`. El modelo es acotado: el proyecto parametriza, pero no agrega ni reordena etapas ni quita sus gates, y un gancho nuevo requiere su propio hallazgo.

```toml
[stages.implement]
description = "Implement the approved change within its declared scope."
ai = true
role = "implementer"
checkpoint = { decider = "owner", criteria = [], on_reject = "revise" }   # activa pre-implement
```

### Acuerdo del flujo

El flujo se acuerda como una referencia con rol `process`, para cada componente. Los comandos son los de las demás referencias; repite `--component` por cada componente:

```bash
roclec --project ROOT --json skills
roclec --project ROOT --json reference add flow --path .roclec/flow.toml --role process --component COMPONENT
roclec --project ROOT --json foundation agree --ref flow --actor "Responsable" --reason "Flujo acordado" --criteria criterios.json
roclec --project ROOT --json views --write
```

Editar el flujo lo deja `stale`: el gate de implementación y el de release se bloquean hasta acordarlo de nuevo. `change approve` fija la huella del flujo vigente y cada decisión con criterios registra el flujo con el que se tomó; una decisión posterior no se reevalúa contra un flujo editado.

### Evaluación de criterios

Toda decisión en un punto declarado (`change approve`, `foundation agree`, `checkpoint` y `reject`) lleva `--criteria FILE`, la evaluación de la persona:

```json
[{"id": "CR-001", "status": "met", "reason": "Coincide con la práctica acordada"}]
```

Reglas: la lista cubre exactamente los criterios del punto (`CRITERIA_MISMATCH` si falta o sobra alguno); `status` es `met`, `not-met` o `n/a`, y `n/a` exige `reason`. Una aprobación no admite `not-met` (`CRITERIA_NOT_MET`). Un rechazo de un punto con criterios cita al menos uno `not-met` (`CRITERIA_REQUIRED`). Los puntos son: `change approve` y `reject change`, approve; `foundation agree` y `reject adr|reference`, foundation; `checkpoint` y `reject prototype`, design. Sin `--consequence`, se usa el `on_reject` del punto. Roclec comprueba la presencia y la coherencia de la evaluación, no que sea verdadera; solo la persona la completa.

### Puntos de control de gancho

Un gancho declarado bloquea sus gates hasta que una persona lo aprueba. Se decide sobre una huella concreta:

```bash
roclec --project ROOT --json checkpoint CHG-001 --hook pre-implement --component COMPONENT --digest SHA --outcome approved --actor "Responsable" --reason "Listo para implementar" --criteria criterios.json
roclec --project ROOT --json checkpoint CHG-001 --hook pre-integrate --component COMPONENT --run RUN-001 --digest SHA --outcome approved --actor "Responsable" --reason "Candidato aceptado" --criteria criterios.json
roclec --project ROOT --json checkpoint CHG-001 --hook handoff --component COMPONENT --digest SHA --outcome rejected --consequence defer --fut FUT-001 --corrections correcciones.json --actor "Responsable" --reason "Se difiere" --criteria criterios.json
```

| Gancho | Huella (`--digest`) | Bloquea hasta la aprobación |
| --- | --- | --- |
| `pre-implement` | Digest de la propuesta | Gates de implementación, verificación e integración |
| `pre-integrate` | `inputs_digest` del candidato del run `--run` | Gate de integración e `integrate prepare` |
| `handoff` | Digest del registro de integración | Gate de release y `release prepare` |

Sin la aprobación vigente, el gate falla con `CHECKPOINT_REQUIRED` y su remediación nombra el comando exacto. Una aprobación vale solo para la huella actual y después del último rechazo `revise`. Consecuencias de un rechazo: `revise` espera un digest nuevo y las respuestas `--addresses` a las correcciones; `cancel` se acompaña de `change cancel`; `handoff` solo admite `defer` con un FUT, y permite retirar ese miembro de la release en planificación. Ni el gate ni un agente registran estas decisiones por la persona.

### Vista generada y avisos

`views --write` genera `docs/flow.md` (configurable con `view` en el flujo): una tabla, los criterios y un diagrama Mermaid, con un encabezado administrado y su SHA-256. No lo edites a mano. `check` informa `FLOW_VIEW_STALE` si el flujo cambió, `FLOW_VIEW_EDITED` si la vista tiene ediciones locales, `FLOW_MISSING` si el archivo no existe y `FLOW_CRITERION_UNUSED` si un criterio no lo cita ningún punto, todos como avisos. Un flujo inválido produce el error `FLOW_INVALID`.

### Conformidad con el flujo

`inspect --change CHG-001` agrega la sección `flow`: la huella del flujo vigente, si está acordado (`agreed`), la huella con la que se aprobó el cambio (`approved_under`) y, por etapa y componente, un estado `done`, `pending`, `blocked` o `n/a` con el registro que la cumplió, el actor declarado y los criterios evaluados. En un punto humano pendiente, `pending` indica quién decide y qué criterios presentar, con su texto; los hooks aparecen bajo su etapa. La sección es de solo lectura: no ejecuta checks ni consulta remotos (`verify` refleja la última run registrada; `--deep` o `check --gate verify` vuelven a evaluar el candidato). Para una etapa con `ai = false`, Roclec registra el actor declarado y no puede probar quién la ejecutó; la sección lo indica en `limitation`.

### Migrar un proyecto existente

El flujo obligatorio rompe la compatibilidad desde 0.9.0. En un proyecto anterior: ejecuta `roclec skills` para sembrar `.roclec/flow.toml`, `roclec views --write`, registra la referencia `process` y acuérdala para cada componente. Desde entonces las aprobaciones, los acuerdos y los puntos de control necesitan `--criteria`.

Cambios de 0.9.0 en las skills de conocimiento:

- Los nombres de `skills` en una etapa del flujo ahora deben ser referencias registradas con rol `skill` (`FLOW_SKILL_UNREGISTERED`) y cumplir `[a-z][a-z0-9-]*`; antes solo se validaba el patrón `[a-z0-9][a-z0-9-]*`, así que un nombre que empieza por dígito era válido y ahora no.
- Las decisiones de aprobación escritas por 0.9.0 pueden llevar `skills`. Siguen en `model_schema: 2`, el esquema único de 0.9.0; un lector 0.8.0 (esquema 1) rechaza cualquier registro de 0.9.0 con `UNSUPPORTED_SCHEMA`. Las compilaciones de desarrollo de 0.9.0 no se publicaron y no tienen compatibilidad garantizada.
- `inspect --reference` puede informar `stale` para una referencia acordada y luego editada.
- Ejecuta `roclec skills` para sembrar `.roclec/templates/skill-template.md` y regenerar el mapa de autoridad en `AGENTS.md` y `CLAUDE.md`.

## Releases y FUT

`release plan` reemplaza explícitamente pertenencia de una versión planning; repetir `--change` para todos sus miembros. `--clear` vacía la planificación, sin borrar historia ni desbloquear contenido publicado. Pertenencias viven solo en `release.json`. Correcciones necesitan base registrada como publicada y tag Git real que resuelva al commit registrado; C1 lee ese historial, aún no lo crea. No se crean ni empujan tags.

```bash
roclec --project ROOT --json fut capture --file descubrimiento.json
roclec --project ROOT --json fut decide FUT-001 --outcome evaluating --actor "Responsable" --reason "Investigar impacto"
roclec --project ROOT --json fut decide FUT-001 --outcome promoted --target CHG-001 --actor "Responsable" --reason "Destino acordado"
```

FUT declara `model_schema`, `id`, `source: {location, locator}`, `finding`, `impact`, `questions`. Promoción exige CAP/REQ/CHG o decisión de fundación existente y no aprueba su destino. Un origen `fut` debe estar promovido al cambio o marcado como duplicado suyo. Importa primero el borrador, registra la decisión y comprueba el gate de aprobación. duplicate puede apuntar a otro FUT sin ciclos o directamente al cambio. Reevaluar un hallazgo resuelto exige nueva decisión evaluating y conserva las anteriores.

## Consulta y recuperación

`status` resume los cambios, gates pendientes, ejecuciones sin finalizar y releases en planificación por componente. `list changes|futs|releases|runs|adrs|rejections` consulta cada colección; `status` incluye por componente los ADR `proposed` o `stale` en `pending_adrs`. `list changes --origin ID` busca cambios en cualquier estado por el ID declarado, independientemente del tipo o localizador. `inspect --change CHG-001` muestra sus orígenes y cobertura. Usa `--json` para automatización y `--debug` para obtener la traza de un error interno.

`inspect --capability CAP-001` muestra el vector por componente. `--component NAME --at VERSION` resuelve el contrato histórico de una publicación registrada. `views --write` genera vistas; una edición manual no resuelta bloquea sobrescritura. Proponer cambios no retira AC del contrato integrado.

Las mutaciones validan antes de escribir, vuelven a comprobar precondiciones bajo lock y dejan recibo. Los diarios de C1 son internos, no planes externos ejecutables. Ante exit 4/IO_PARTIAL conservar los archivos y ejecutar `operation inspect ID` y `operation recover ID` con `--project` en la raíz exacta. Recovery funciona aun si falta parte de la inicialización. Una divergencia posterior bloquea recuperación; repetir una ya completada no repite efectos.

El lock local no coordina máquinas/worktrees remotos. Si un proceso muere dejando `.roclec/runtime/lock`, verificar que no sigue activo antes de retirar el directorio vacío del lock y recuperar su journal. No borrar diarios para ocultar fallos. Los gates finales limpios de D2 llegarán con C2; no se realizan commits automáticos.

Un exit 0 de C1 acredita la operación de definición solicitada, no verificación del código, integración ni publicación. Los códigos y sobre JSON están en las interfaces.
