# Uso de C2: evidencia e integración

Esta guía describe el perfil 3 y el modelo 2 en desarrollo. Los nombres de componentes, herramientas y criterios pertenecen al consumidor. [Decisiones del Hito 02](strategy/plan-global.md)

## Declarar entradas y comprobaciones

Ejemplo de componente, sobre un perfil con fundación y cambio aprobados:

```toml
[components.engine]
repo = "../engine"
target_ref = "refs/remotes/origin/main"
user_facing = false
inputs = ["src/**", "tests/**", "pyproject.toml", "uv.lock"]
generated = ["build/**", "__pycache__/**"]
excluded = [".venv/**", "private.env"]
verification = [{id="unit", argv=["python3", "-m", "unittest", "discover", "-s", "tests"], cwd=".", timeout_seconds=60, acceptance_ids=["AC-001"]}]
```

`excluded` y `acceptance_ids` son opcionales. La relación check–AC es una declaración revisable, no prueba de suficiencia semántica. Un check sin esa relación puede ejecutarse y pasar, pero no cubre AC por defecto. Los patrones se comparan con rutas POSIX relativas al repo mediante glob (`*`, `?`, clases; `**` coincide también con `/`). El consumidor clasifica lockfiles, checks, configuración y dependencias compartidas relevantes como entradas. Las referencias acordadas y `.gitignore` también son entradas. Una ruta que coincida con entrada y salida/exclusión bloquea el candidato.

Se enumeran archivos de Git, nuevos, ignorados y rutas de la base/diff; fuentes nuevas y eliminaciones cambian el manifiesto. Una ruta sin clasificación bloquea sin leer sus bytes. Los ignorados no son irrelevantes automáticamente: una fuente ignorada declarada como input se captura; exclusiones y salidas explícitas no se leen. No se infieren categorías según stack. Los componentes que comparten repo comparten la clasificación de sus entradas; sus AC y gates permanecen separados.

## Ejecutar y comprobar

```bash
roclec --project ROOT --json run verify CHG-001 --component engine --base BASE_COMMIT --role implementer --context "SESIÓN_O_HERRAMIENTA"
roclec --project ROOT --json check --change CHG-001 --component engine --gate verify
```

`--role` (`implementer`, `coordinator` o `human`) y `--context` (identidad real de la sesión o herramienta, en una línea) son obligatorios; el run los guarda como `producer: {role, context}`. `--base` debe resolver a un commit ancestro de HEAD del repo configurado. Se admite trabajo sin commit durante desarrollo. El manifiesto identifica base/HEAD, archivos y modos o eliminaciones, propuesta, perfil/checks, referencias acordadas y ejecutables disponibles con sus hashes. No incluye el índice ni sus propios runs/recibos como código. No pretende capturar todo el entorno o hacer hermética una herramienta externa: el consumidor debe declarar entradas suficientes.

Ejecuta `run verify` solo en repositorios de confianza. `argv` ejecuta comandos del perfil en su cwd con timeout. El entorno incluye `PATH`, `HOME`, `TMPDIR`, `LANG`, `LANGUAGE` y variables `LC_*` que existan. Cada check puede ampliar la lista con `env`. El manifiesto registra los nombres que recibió.

La cuota `log_quota_bytes` del perfil es de 16 MiB por run de forma predeterminada. Las capturas crudas de stdout y stderr quedan en `.roclec/runtime/logs/`. El manifiesto conserva ruta lógica, SHA-256, tamaño y completitud. Agotar la cuota o fallar al escribir detiene el check y deja el run incompleto. Una interrupción abrupta puede dejar solo el inicio. Ambos casos bloquean el gate.

`max_log_bytes` limita el extracto de cada flujo y vale 0 por defecto. Los extractos reemplazan los valores de `secret_env` y las coincidencias de `redact_patterns` dentro del texto capturado para el extracto. Conserva los logs completos localmente si necesitas auditarlos. `check` avisa con `LOG_UNAVAILABLE` cuando faltan y con `CHECK_ARGV_CHANGED` cuando cambió el comando. El gate puede evaluar un manifiesto completo en un clon sin logs.

`data.recorded=true` distingue una ejecución persistida de un rechazo de preflight. Exit 1 puede conservar checks pass si falta cobertura o revisión. Exit 130 conserva la interrupción cuando fue posible finalizar el registro. El gate evalúa la única cabeza causal del ámbito y valida sus entradas. Ante cabezas concurrentes, ejecuta un nuevo run para sustituirlas.

## Adjuntar observación o revisión

`evidence record --file FILE` importa este objeto; RUN y DIGEST se toman del run real:

```json
{
  "model_schema": 2,
  "kind": "manual",
  "change_id": "CHG-001",
  "component": "engine",
  "run_id": "RUN-01ARZ3NDEKTSV4RRFFQ69G5FAV",
  "candidate_digest": "DIGEST",
  "actor": "Responsable de la observación",
  "context": "Dispositivo, entorno y alcance observados",
  "outcome": "pass",
  "acceptance_ids": ["AC-001"],
  "checks": ["Observación concreta y su resultado"],
  "limitations": [],
  "findings": []
}
```

Kinds: `manual`, `automated-import`, `independent-review`. Los dos primeros usan outcome `pass|fail|incomplete`; la revisión usa `ready|changes-needed|incomplete`. Todos conservan `executed_by_roclec=false`: un informe importado no acredita ejecución de un subprocess por Roclec. Cada hallazgo nuevo tiene `id`, severidad, ubicación, criterios afectados, condición, impacto y descripción. Se asigna EVD sin sobrescribir informes anteriores. El digest debe coincidir con `data.run.candidate.inputs_digest`; un AC ajeno o una huella obsoleta se rechazan antes de escribir. Para cada AC se aplica la última observación vigente: un pass anterior no oculta una observación posterior fail/incomplete.

```bash
roclec --project ROOT --json review policy --change CHG-001 --enabled true --actor "Responsable" --reason "Decisión explícita"
roclec --project ROOT --json evidence record --file informe.json
```

Un informe independent-review añade `policy_id` de la política vigente (`data.review_policy.id` en inspect del cambio o de la release) y `role` (`reviewer` o `human`). Su `context` debe diferir del `producer.context` del run (sin distinguir mayúsculas ni espacios en los extremos); si coincide se rechaza con `SELF_REVIEW_DECLARED`. Un run sin `producer` no respalda revisiones: repite `run verify` con `--role` y `--context`. Roclec compara contextos declarados, no independencia real. Cuando se habilita la política, se exige un `ready` vigente con comprobaciones. Cualquier dictamen adverso vigente bloquea el gate. Cada revisor sustituye su propia cabeza. Las observaciones se sustituyen por AC, por lo que repetir un criterio conserva los dictámenes de los demás. El CLI rellena `supersedes`. Usa un nuevo informe para conciliar cabezas concurrentes del mismo ámbito.

## Ciclo de vida de hallazgos

Desde 0.9.0, la revisión está habilitada por defecto, incluso si el perfil omite la sección. El umbral material predeterminado es `major`. El proyecto puede definirlo en su perfil y un cambio puede desactivar la revisión mediante una decisión con actor y motivo. Al actualizar un proyecto sin decisión de política, consulta el nuevo `policy_id` con `inspect` y registra una revisión vigente. Los informes anteriores se conservan como historial.

```toml
[review]
enabled = true
material_severity = "major"
```

Cada hallazgo usa `id` con forma `F-n` único en su informe, `severity` (`blocker`, `major`, `minor` o `info`), `location` como `{ "path": "ruta", "line": 1 }` o `null`, `acceptance_ids`, `condition`, `impact` y `description`. Su clave estable es `EVD-ID#F-n`. Los hallazgos históricos sin severidad conservan su identificador original y se tratan como `major`. Si un hallazgo corregido reaparece, registra uno nuevo con `recurs_from` apuntando a la clave anterior.

Una revisión incluye `resolutions`, una lista de objetos con `finding`, `status` (`fixed` o `still-open`), `candidate_digest` del candidato examinado y `note`. La revisión debe incluir todos los hallazgos abiertos o aún abiertos de su alcance, incluso los de informes históricos. Un revisor independiente verifica la corrección. El implementador cita las claves atendidas en su resumen.

El usuario puede aceptar un riesgo, invalidar un hallazgo o diferirlo a un FUT existente. Una decisión se importa con `evidence record --file decision.json` y puede registrarse desde un worktree:

```json
{
  "model_schema": 2,
  "kind": "finding-decision",
  "change_id": "CHG-001",
  "component": "engine",
  "actor": "Responsable",
  "reason": "Explicación de la decisión",
  "findings": ["EVD-01ARZ3NDEKTSV4RRFFQ69G5FAV#F-1"],
  "status": "deferred",
  "fut_id": "FUT-001"
}
```

Los estados posibles de la decisión son `accepted`, `invalid` y `deferred`. El último requiere `fut_id`; los hallazgos se enumeran en orden y sin duplicados. La decisión puede incluir `severity` para registrar una reclasificación al cerrar el hallazgo. Para decidir sobre un hallazgo propio de la release, usa `change_id: null` y añade `release` con `component` y `version`. Para un hallazgo de un miembro, usa el alcance del cambio. Publicar la release cierra el registro de sus propios hallazgos, resoluciones y decisiones. Los informes con listas vacías de hallazgos y resoluciones se pueden registrar después de publicar.

```bash
roclec --project ROOT --json inspect --change CHG-001
roclec --project ROOT --json list findings --change CHG-001 --open
roclec --project ROOT --json list findings --release v1.0.0 --component engine
```

El estado se deriva de la evidencia y se conserva al cambiar de candidato. Las transiciones concurrentes que coinciden conservan el estado acordado y la decisión humana prevalece sobre la revisión concurrente. Si los revisores discrepan sobre una corrección, el hallazgo queda en `still-open` hasta que un revisor confirme la corrección o el usuario decida su disposición. Si las decisiones humanas discrepan, el usuario concilia el resultado. Con revisión habilitada, los gates de verificación e integración exigen un informe `ready` vigente y bloquean los hallazgos abiertos en el umbral material o superior. Los abiertos de menor severidad se informan. La verificación final aplica el gate de revisión a los hallazgos propios de la release. El gate de release lista hallazgos de sus miembros y de la propia release, incluidos los abiertos, aceptados y diferidos. Si cambia el estado de los hallazgos después de preparar la release, genera otra preparación antes de registrar la publicación.

## Sesiones de agente como evidencia

Una sesión de agente se importa como evidencia opaca: Roclec guarda el archivo que exportó el host y no interpreta su formato. Funciona en cualquier rama, como el resto de `evidence record`.

```bash
roclec --project ROOT --json evidence record --kind agent-session --file META.json --transcript EXPORT
```

`META.json` declara `model_schema` (2), `host`, `host_session_id`, `actor`, `role`, `model`, `started_at`, `ended_at` (UTC, `YYYY-MM-DDTHH:MM:SSZ`, sin que el fin preceda al inicio) y `stage`, y no declara `kind`. El rol es uno de Roclec o un rol `agent` del flujo. El ámbito depende de la etapa:

| Etapa | Ámbito requerido |
| --- | --- |
| `foundation` | `subject`: una referencia o ADR registrado |
| `release` | `release` `{component, version}` de una release planificada |
| `define`, `approve`, `plan` | `change_id`; `component` opcional. Una sesión de `define` puede nombrar un CHG que aún no se importó, para que el primer bundle cite la sesión que lo redactó (sin componente) |
| `design`, `implement`, `verify`, `review`, `integrate` | `change_id` y `component` dentro del alcance del cambio |

El original se conserva byte a byte en `.roclec/runtime/sessions/EVD-ID/NOMBRE`, local, fuera de Git y con permisos solo del propietario. El registro `.roclec/evidence/EVD-ID.json` guarda su SHA-256 y su tamaño, `executed_by_roclec=false` y el modo de almacenamiento. Una sesión no es un informe: no cubre criterios de aceptación, no sustituye informes ni lleva hallazgos. Para obtener la exportación en Claude Code o Codex y rellenar los metadatos, sigue la [referencia del coordinador](../src/roclec_spec_kit/assets/skills/roclec-coordinator/references/session-export.md); no se duplica aquí porque la ubicación de los archivos depende del host.

### Cuota y almacenamiento

`[sessions] quota_bytes` limita el tamaño de cada transcript (16 MiB por defecto). Si lo supera, la importación se rechaza con `SESSION_QUOTA_EXCEEDED`, sin escribir nada; nunca se trunca. `[sessions] storage` elige qué entra en Git:

```toml
[sessions]
storage = "versioned-redacted"   # local | versioned-redacted (por defecto) | versioned-raw
quota_bytes = 16777216
```

| Política | Qué queda en Git |
| --- | --- |
| `local` | Solo el registro: metadatos, huella y tamaño |
| `versioned-redacted` (por defecto) | Además, `EVD-ID.session`: una copia en UTF-8 estricto cuyo único cambio es reemplazar por `[REDACTED]` cada valor de `secret_env` y cada coincidencia de `redact_patterns`. El registro guarda el número de reemplazos y la huella de la copia, junto con la del original |
| `versioned-raw` | Una copia idéntica al original. Debe elegirse explícitamente |

La redacción cubre los valores de `secret_env` (también en sus formas escapadas como JSON, porque los transcripts suelen ser JSON por líneas) y los patrones de `redact_patterns`, y nada más. Las advertencias relacionadas son:

- `SESSION_SECRET_UNSET`: variables de `secret_env` sin valor al importar; sus valores no se redactaron. Importa desde un shell donde estén definidas.
- `SESSION_REDACTION_EMPTY`: no había ningún valor ni patrón con que redactar, así que la copia versionada no está redactada. Declara `secret_env` o `redact_patterns`, o usa `storage = "local"`.
- `SESSION_RAW_VERSIONED`: la política `versioned-raw` puede versionar secretos.
- `RUNTIME_NOT_IGNORED`: no es una advertencia, es un rechazo de la importación. `.roclec/runtime/` debe estar ignorado por Git; `roclec skills` restaura la línea de `.gitignore`.

`check` también informa `SESSION_RAW_UNAVAILABLE` cuando falta el original local, por ejemplo en un clon nuevo. Es una limitación que no bloquea: los gates siguen evaluando el registro versionado, igual que con `LOG_UNAVAILABLE`. Informa `SESSION_RAW_ORPHAN` para un original local sin registro y `HASH_MISMATCH` si el original o la copia versionada se editaron después de importarlos.

### Privacidad

Los transcripts contienen código, rutas, nombres y posibles datos personales. Revisa `[sessions] storage` antes de versionar sesiones, y elige `local` si dudas. Roclec solo redacta lo que el perfil declara; el consumidor es responsable de todo lo demás que contenga el transcript, igual que del texto que captura de un origen al sellar un cambio.

### Citar sesiones y exigirlas

Los registros citan las sesiones que los produjeron con `--session EVD-ID` (repetible) en `change approve`, `change cancel`, `change start`, `foundation agree`, `reject`, `checkpoint`, `fut decide` y `run verify`. Un bundle las lista en `semantic.sessions` (`change seal` y `change new` las comprueban) y la evidencia manual, importada o de revisión las declara en su JSON. Cada ID debe ser una sesión existente y de ámbito compatible (el mismo cambio, la misma release o, en `foundation agree`, la misma referencia); si no, se rechaza con `INVALID_REFERENCE` sin escribir. `inspect --change` muestra en cada etapa las sesiones que intervinieron.

En una revisión independiente, `context` pasa a ser el ID de la sesión del revisor (rol `reviewer`, etapa `review`, mismo cambio y componente) cuando la etapa `review` exige sesiones. Una sesión de revisión citada por el propio run, o con el mismo `host_session_id` que una sesión que el run cita, es `SELF_REVIEW_DECLARED`. Con `session_evidence = "optional"` el texto libre se admite, pero un contexto con forma de EVD debe resolver a esa sesión. La exigencia solo aplica a revisiones de un cambio: en una revisión de release, `context` sigue siendo texto libre o el ID de una sesión de etapa `release` y rol `reviewer` de esa misma release. Una revisión humana requiere que la etapa `review` sea `optional`.

`session_evidence` se declara por etapa en `.roclec/flow.toml` y solo admite `required` con `ai = true`. El flujo sembrado la exige en todas las etapas con IA. Con `required`, el gate que cierra la etapa pide al menos una sesión de esa etapa y ámbito, y falla con `SESSION_REQUIRED` indicando qué importar:

| Etapa | Gate que la exige |
| --- | --- |
| `foundation` | `foundation agree` (sesión cuyo `subject` es la referencia) |
| `define` | gate de aprobación y `change approve` |
| `design` (componentes con interfaz de usuario) y `plan` | gate de implementación |
| `implement` | gate de verificación |
| `verify` y `review` (con la revisión habilitada) | gate de integración |
| `integrate` | gate de release, por cada miembro del componente de la release |
| `release` | `release record` |

Las etapas anteriores se comprueban con el flujo acordado: el gate de implementación vuelve a comprobar `define` y `foundation`. Un componente ya integrado no se vuelve a evaluar por sus etapas anteriores.

## Aprendizaje del flujo

Una fricción del flujo (un gate que estorba, un rol que no rinde, una etapa que convendría hacer sin IA) se captura como FUT con `scope` `process`; sin `scope`, el FUT es `product`. `list futs` e `inspect --fut` muestran el ámbito.

```bash
roclec --project ROOT --json foundation agree --ref flow --fut FUT-007 --actor "Responsable" --reason "Motivo del ajuste" --criteria criterios.json
roclec --project ROOT --json fut decide FUT-007 --outcome promoted --target DECISION_SHA --actor "Responsable" --reason "Atendido por el acuerdo"
roclec --project ROOT --json inspect --fut FUT-007
```

`--fut` (repetible, solo para una referencia `process`) registra en el acuerdo los FUT abiertos de proceso que atiende, de modo que quede la cadena fricción, ajuste del flujo y motivo, con el actor real. Después, `fut decide --outcome promoted --target` solo admite como destino una decisión que cite ese FUT, y un FUT de producto no se promueve a un acuerdo del flujo. `inspect --fut` muestra `addressed_by`: la decisión, los bytes del flujo acordados, el motivo y el actor.

`roclec views --write` añade a la vista del flujo (`docs/flow.md` o la ruta `view`) una sección «Flow learning». Solo contiene contenidos derivados de los registros, sin juicios: revisiones del flujo con sus FUT y motivos, FUT de proceso abiertos, rechazos por etapa, hallazgos por severidad y estado, etapas con `ai = false` con su motivo, y sesiones por rol y etapa. Cuando hay registros nuevos, `check` avisa con `FLOW_VIEW_STALE` hasta regenerarla. `views --write` solo se ejecuta en la troncal: en una rama, el aviso persiste hasta fusionar el trabajo y ejecutar `views --write` allí.

`docs/flow-retro.md` es una plantilla de retrospectiva del consumidor que Roclec siembra una vez y nunca sobrescribe. Úsala para lo que los registros no derivan: qué no funcionó, qué cambiaría con un equipo mayor y qué decisiones de uso de IA revisar. Una reflexión que lleve a ajustar el flujo se captura como FUT `process` y se cita al acordarlo.

## Actualizar un proyecto existente

- Un flujo que declare `session_evidence = "required"` en una etapa con `ai = false` es ahora `FLOW_INVALID`: quita el campo o usa `"optional"` y vuelve a acordar el flujo.
- Un flujo existente conserva su configuración: sin `session_evidence`, el valor es `optional`. Los proyectos nuevos se siembran con sesiones exigidas en las etapas con IA; un proyecto existente las adopta editando su flujo y acordándolo de nuevo.
- Tras registrar evidencia, decisiones o FUT, `check` avisa con `FLOW_VIEW_STALE` hasta ejecutar `views --write` en la troncal.
- Skills de conocimiento (0.9.0): las decisiones de aprobación pueden llevar `skills`, dentro del mismo `model_schema: 2`; ver [Skills de conocimiento](c1.md#skills-de-conocimiento) y sus notas de migración.
- Los campos y flags nuevos (`sessions`, `--session`, `--fut`, `scope`) son aditivos y se omiten cuando están vacíos, de modo que los digests de los registros anteriores no cambian.

## Preparar, aplicar y recuperar

Antes del gate final, confirmar los cambios en los repos de código afectados, incluidos metadatos de runs/revisión cuando residan allí. Roclec no realiza commits. Staged, unstaged y untracked no ignorados bloquean en todo el repo afectado. Si el nuevo commit conserva entradas verificadas, ámbito, política y ascendencia, se puede reutilizar la evidencia; HEAD por sí solo nunca concede pass.

```bash
roclec --project ROOT --json check --change CHG-001 --component engine --gate integrate
roclec --project ROOT --json integrate prepare CHG-001 --component engine --run RUN-ID --out /tmp/integration.json
roclec --project ROOT --json operation apply /tmp/integration.json
roclec --project ROOT --json inspect --change CHG-001
```

Exportar el plan fuera de los repos de código evita añadir trabajo pendiente antes de apply. El destino debe ser nuevo, con directorio existente y fuera de autoridades. Prepare solo escribe ese plan; apply reconstruye sus escrituras y vuelve a validar bajo lock. Un plan alterado, token obsoleto, base movida o código divergente no avanza el índice. Snapshots primero, un reemplazo de `current.json` después y registro/recibo durables al completar. Solo avanza el componente solicitado; los demás mantienen base/contrato. El agregado muestra partially-integrated hasta completar sus participantes.

Las escrituras de integración son efectos posteriores al preflight; si comparten repo con código, se confirman antes del siguiente gate final. Cancelar afecta solo participantes pendientes; una parte ya integrada requiere un cambio de reversión y no puede retirarse de su release. El registro identifica la revisión y candidato exactos por componente.

Si un participante pendiente necesita rebase o aclaración de intención, se edita su borrador conforme al formato C1, se recalculan hashes y se registra una aprobación nueva. Se vuelve a asignar esa revisión a la release del participante pendiente y se obtiene evidencia vigente. El participante integrado conserva su aprobación, release y candidato originales; inspect muestra esas revisiones en `integrations`. La nueva revisión no puede retirarlo ni cambiar sus obligaciones/AC/textos: eso requiere otro cambio. Un cambio totalmente integrado permanece histórico.

Actualiza la referencia remota configurada con Git antes de preparar. El plan conserva `target_ref` y `target_commit` y exige que el candidato sea ancestro de esa punta. Si cambia antes de aplicar, exporta un nuevo plan. Las consultas y exportaciones funcionan en cualquier rama. Aplicar y editar autoridades exige `trunk_ref`. Solo inicio de cambio, ejecución y evidencia escriben registros de trabajo fuera de esa rama.

Ante `IO_PARTIAL`, usa `operation inspect ID` y `operation recover ID`. Si el destino cambia antes del recibo, la recuperación restaura los bytes previos o retira los archivos creados. Las divergencias requieren resolución antes de reintentar. Si el recibo válido ya existe, la recuperación conserva la operación confirmada. `operation unlock --if-stale` comprueba propietario y proceso local. Fuera de la troncal, solo recupera o desbloquea operaciones admitidas en ramas.

`check` sin gate valida estructura e informa `unfinished_runs`; no declara verificados todos los componentes. Preparación/publicación de releases y el gate release se describen en la [guía C3](c3.md). [Evidencia de implementación C2](implementation/c2.md).
