# Uso de C2: evidencia e integración

Esta guía describe el perfil 3 y el modelo 2 en desarrollo. Los nombres de componentes, herramientas y criterios pertenecen al consumidor. [Decisiones del Hito 02](strategy/plan-global.md)

## Declarar entradas y comprobaciones

Ejemplo de componente, sobre un perfil con fundación y cambio aprobados:

```toml
[components.engine]
repo = "../engine"
target_ref = "refs/remotes/origin/main"
user_facing = false
inputs = ["src/**", "tests/**", "pyproject.toml", "uv.lock"]
generated = ["build/**", "__pycache__/**"]
excluded = [".venv/**", "private.env"]
verification = [{id="unit", argv=["python3", "-m", "unittest", "discover", "-s", "tests"], cwd=".", timeout_seconds=60, acceptance_ids=["AC-001"]}]
```

`excluded` y `acceptance_ids` son opcionales. La relación check–AC es una declaración revisable, no prueba de suficiencia semántica. Un check sin esa relación puede ejecutarse y pasar, pero no cubre AC por defecto. Los patrones se comparan con rutas POSIX relativas al repo mediante glob (`*`, `?`, clases; `**` coincide también con `/`). El consumidor clasifica lockfiles, checks, configuración y dependencias compartidas relevantes como entradas. Las referencias acordadas y `.gitignore` también son entradas. Una ruta que coincida con entrada y salida/exclusión bloquea el candidato.

Se enumeran archivos de Git, nuevos, ignorados y rutas de la base/diff; fuentes nuevas y eliminaciones cambian el manifiesto. Una ruta sin clasificación bloquea sin leer sus bytes. Los ignorados no son irrelevantes automáticamente: una fuente ignorada declarada como input se captura; exclusiones y salidas explícitas no se leen. No se infieren categorías según stack. Los componentes que comparten repo comparten la clasificación de sus entradas; sus AC y gates permanecen separados.

## Ejecutar y comprobar

```bash
roclec --project ROOT --json run verify CHG-001 --component engine --base BASE_COMMIT
roclec --project ROOT --json check --change CHG-001 --component engine --gate verify
```

`--base` debe resolver a un commit ancestro de HEAD del repo configurado. Se admite trabajo sin commit durante desarrollo. El manifiesto identifica base/HEAD, archivos y modos o eliminaciones, propuesta, perfil/checks, referencias acordadas y ejecutables disponibles con sus hashes. No incluye el índice ni sus propios runs/recibos como código. No pretende capturar todo el entorno o hacer hermética una herramienta externa: el consumidor debe declarar entradas suficientes.

Ejecuta `run verify` solo en repositorios de confianza. `argv` ejecuta comandos del perfil en su cwd con timeout. El entorno incluye `PATH`, `HOME`, `TMPDIR`, `LANG`, `LANGUAGE` y variables `LC_*` que existan. Cada check puede ampliar la lista con `env`. El manifiesto registra los nombres que recibió.

La cuota `log_quota_bytes` del perfil es de 16 MiB por run de forma predeterminada. Las capturas crudas de stdout y stderr quedan en `.roclec/runtime/logs/`. El manifiesto conserva ruta lógica, SHA-256, tamaño y completitud. Agotar la cuota o fallar al escribir detiene el check y deja el run incompleto. Una interrupción abrupta puede dejar solo el inicio. Ambos casos bloquean el gate.

`max_log_bytes` limita el extracto de cada flujo y vale 0 por defecto. Los extractos reemplazan los valores de `secret_env` y las coincidencias de `redact_patterns` dentro del texto capturado para el extracto. Conserva los logs completos localmente si necesitas auditarlos. `check` avisa con `LOG_UNAVAILABLE` cuando faltan y con `CHECK_ARGV_CHANGED` cuando cambió el comando. El gate puede evaluar un manifiesto completo en un clon sin logs.

`data.recorded=true` distingue una ejecución persistida de un rechazo de preflight. Exit 1 puede conservar checks pass si falta cobertura o revisión. Exit 130 conserva la interrupción cuando fue posible finalizar el registro. El gate evalúa la única cabeza causal del ámbito y valida sus entradas. Ante cabezas concurrentes, ejecuta un nuevo run para sustituirlas.

## Adjuntar observación o revisión

`evidence record --file FILE` importa este objeto; RUN y DIGEST se toman del run real:

```json
{
  "model_schema": 2,
  "kind": "manual",
  "change_id": "CHG-001",
  "component": "engine",
  "run_id": "RUN-01ARZ3NDEKTSV4RRFFQ69G5FAV",
  "candidate_digest": "DIGEST",
  "actor": "Responsable de la observación",
  "context": "Dispositivo, entorno y alcance observados",
  "outcome": "pass",
  "acceptance_ids": ["AC-001"],
  "checks": ["Observación concreta y su resultado"],
  "limitations": [],
  "findings": []
}
```

Kinds: `manual`, `automated-import`, `independent-review`. Los dos primeros usan outcome `pass|fail|incomplete`; la revisión usa `ready|changes-needed|incomplete`. Todos conservan `executed_by_roclec=false`: un informe importado no acredita ejecución de un subprocess por Roclec. Cada hallazgo contiene `id` estable y `description`. Se asigna EVD sin sobrescribir informes anteriores. El digest debe coincidir con `data.run.candidate.inputs_digest`; un AC ajeno o una huella obsoleta se rechazan antes de escribir. Para cada AC se aplica la última observación vigente: un pass anterior no oculta una observación posterior fail/incomplete.

```bash
roclec --project ROOT --json review policy --change CHG-001 --enabled true --actor "Responsable" --reason "Decisión explícita"
roclec --project ROOT --json evidence record --file informe.json
```

Un informe independent-review añade `policy_id` de la decisión vigente (`data.policy.id`). Cuando se habilita la política, se exige un `ready` vigente con comprobaciones. Cualquier dictamen adverso vigente bloquea el gate. Cada revisor sustituye su propia cabeza. Las observaciones se sustituyen por AC, por lo que repetir un criterio conserva los dictámenes de los demás. El CLI rellena `supersedes`. Usa un nuevo informe para conciliar cabezas concurrentes del mismo ámbito.

## Preparar, aplicar y recuperar

Antes del gate final, confirmar los cambios en los repos de código afectados, incluidos metadatos de runs/revisión cuando residan allí. Roclec no realiza commits. Staged, unstaged y untracked no ignorados bloquean en todo el repo afectado. Si el nuevo commit conserva entradas verificadas, ámbito, política y ascendencia, se puede reutilizar la evidencia; HEAD por sí solo nunca concede pass.

```bash
roclec --project ROOT --json check --change CHG-001 --component engine --gate integrate
roclec --project ROOT --json integrate prepare CHG-001 --component engine --run RUN-ID --out /tmp/integration.json
roclec --project ROOT --json operation apply /tmp/integration.json
roclec --project ROOT --json inspect --change CHG-001
```

Exportar el plan fuera de los repos de código evita añadir trabajo pendiente antes de apply. El destino debe ser nuevo, con directorio existente y fuera de autoridades. Prepare solo escribe ese plan; apply reconstruye sus escrituras y vuelve a validar bajo lock. Un plan alterado, token obsoleto, base movida o código divergente no avanza el índice. Snapshots primero, un reemplazo de `current.json` después y registro/recibo durables al completar. Solo avanza el componente solicitado; los demás mantienen base/contrato. El agregado muestra partially-integrated hasta completar sus participantes.

Las escrituras de integración son efectos posteriores al preflight; si comparten repo con código, se confirman antes del siguiente gate final. Cancelar afecta solo participantes pendientes; una parte ya integrada requiere un cambio de reversión y no puede retirarse de su release. El registro identifica la revisión y candidato exactos por componente.

Si un participante pendiente necesita rebase o aclaración de intención, se edita su borrador conforme al formato C1, se recalculan hashes y se registra una aprobación nueva. Se vuelve a asignar esa revisión a la release del participante pendiente y se obtiene evidencia vigente. El participante integrado conserva su aprobación, release y candidato originales; inspect muestra esas revisiones en `integrations`. La nueva revisión no puede retirarlo ni cambiar sus obligaciones/AC/textos: eso requiere otro cambio. Un cambio totalmente integrado permanece histórico.

Actualiza la referencia remota configurada con Git antes de preparar. El plan conserva `target_ref` y `target_commit` y exige que el candidato sea ancestro de esa punta. Si cambia antes de aplicar, exporta un nuevo plan. Las consultas y exportaciones funcionan en cualquier rama. Aplicar y editar autoridades exige `trunk_ref`. Solo inicio de cambio, ejecución y evidencia escriben registros de trabajo fuera de esa rama.

Ante `IO_PARTIAL`, usa `operation inspect ID` y `operation recover ID`. Si el destino cambia antes del recibo, la recuperación restaura los bytes previos o retira los archivos creados. Las divergencias requieren resolución antes de reintentar. Si el recibo válido ya existe, la recuperación conserva la operación confirmada. `operation unlock --if-stale` comprueba propietario y proceso local. Fuera de la troncal, solo recupera o desbloquea operaciones admitidas en ramas.

`check` sin gate valida estructura e informa `unfinished_runs`; no declara verificados todos los componentes. Preparación/publicación de releases y el gate release se describen en la [guía C3](c3.md). [Evidencia de implementación C2](implementation/c2.md).
