# Uso de C3: release final e instalación

Perfil 3 en desarrollo. El gate de release vuelve a comprobar que cada commit integrado es ancestro de la punta actual del `target_ref` del componente. La preparación y el registro se exportan desde cualquier rama. Aplicarlos exige la troncal. [Verificación conjunta](decisions/005-final-release-verification.md)

## Verificar el conjunto

La pertenencia se define antes de implementar por `release plan COMPONENT VERSION --change CHG-ID` (repetir --change). Los miembros deben estar integrados en sus revisiones aprobadas. Una release normal parte de la publicación anterior de su componente y aplica los miembros según sus bases explícitas. Los criterios sustituidos dentro del conjunto no se exigen como si siguieran vigentes. Contratos de otras releases pendientes no se atribuyen automáticamente al conjunto. Una corrección histórica parte del baseline_release publicado declarado, sin retroceder current.json.

```bash
roclec --project ROOT --json run verify --release v1.0.0 --component NAME --base BASE_COMMIT --role implementer --context "SESIÓN_O_HERRAMIENTA"
roclec --project ROOT --json inspect --release v1.0.0 --component NAME
roclec --project ROOT --json check --gate release --release v1.0.0 --component NAME
```

Este RUN es distinto del run por CHG: tiene `change_id: null` y `release: {component, version}`. Captura el contrato final y la pertenencia, ejecuta los checks del perfil, conserva logs y exige cobertura de sus AC finales. `--base` es un commit ancestro explícito. La clasificación de nuevas/ignoradas/eliminadas, huellas, herramientas, interrupciones y limitaciones funciona como en C2. Cambiar pertenencia, contratos o entradas vuelve obsoleta su evidencia. Los gates no ejecutan tests.

Las observaciones e informes usan el formato C2 añadiendo `release: {component, version}` y `change_id: null`, junto con el RUN y candidate_digest exactos. Si algún miembro tiene revisión activada, se exige un informe final ready vigente para ese componente/conjunto. `inspect --release` devuelve `review_policy`, cuya identidad deriva de las decisiones activadas de los miembros; el informe cita esa policy_id. No hay adopción global de revisión y los tests pueden ejecutarse antes de recibir el informe. Desactivar participación requiere la decisión por CHG con actor/motivo y conserva informes.

`skills --restore` requiere Node.js y un `skills-lock.json` de versión 1 propio del consumidor. Roclec invoca `skills@1.7.6` en un directorio temporal y verifica cada `computedHash` antes de copiar la skill. El resultado queda bajo `.roclec/runtime/skills/`. Un desajuste devuelve `SKILL_HASH_MISMATCH`. [Algoritmo del instalador fijado](https://github.com/vercel-labs/skills/blob/v1.7.6/src/local-lock.ts)

## Preparar y aplicar

Confirmar todos los archivos pendientes del repo de código afectado, incluidos metadatos operativos si comparten repo. Roclec no hace commits. Normal: incrementar X o Y y reiniciar subordinados, con Z=0. Hotfix/bugfix: solo fixes, mantener X.Y e incrementar Z respecto del historial publicado de esa línea, con un base-tag real.

```bash
roclec --project ROOT --json release prepare NAME v1.0.0 --run RUN-ID --out /tmp/release-prepare.json
roclec --project ROOT --json operation apply /tmp/release-prepare.json
```

Prepare solo exporta el plan. Apply lo reconstruye, revalida versión, pertenencia, integración, dependencias, candidato final limpio, cobertura/revisión y fixes, y crea `.roclec/releases/NAME/v1.0.0/preparations/SHA.json`. SHA es `data.plan.inputs.preparation` y fija candidato/contratos/evidencia. Los intentos anteriores quedan históricos. Repetir apply devuelve el recibo sin efectos nuevos.

## Acreditar fixes y backports

Un CHG fix no tiene deltas/propuestas normativas. Sus `semantic.fixes` indican componente, `commit` como SHA Git completo inmutable, `requirement_ids`, `acceptance_ids` de su base exacta y `backport` null o `{commit: SHA}`. Puede fijarse `backport.evidence_id` explícitamente; si se omite, el gate selecciona una observación de preservación favorable vigente de ese RUN de release y congela su EVD real en la preparación. No hace falta adivinar un ID futuro al aprobar.

El commit original debe existir localmente. La implementación original, o el backport declarado, debe ser ancestro del candidato final. Un backport necesita además observación de preservación actual con los AC restaurados. Un SHA inexistente, un commit de otra rama no incluido o un backport sin evidencia produce FIX_NOT_INCLUDED. Un enlace PR requiere resolver sus commits reales antes de registrar la referencia; el texto del enlace no acredita inclusión. La CLI comprueba relaciones, no que un diff restaure semánticamente una obligación.

## Registrar una publicación existente

El commit preparado es el que se etiqueta y publica mediante herramientas/autorización ajenas a Roclec. La preparación escrita puede introducir metadatos pendientes: si viven en el repo de código, confirmarlos antes del siguiente gate. Esos commits de metadatos pueden descender del preparado con entradas idénticas, pero no cambian el commit enviado en el registro.

```bash
roclec --project ROOT --json release record NAME v1.0.0 \
  --preparation SHA --commit PREPARED_COMMIT --tag v1.0.0 --remote origin \
  --actor "Responsable" --reason "Publicación Git comprobada" --out /tmp/release-record.json
roclec --project ROOT --json operation apply /tmp/release-record.json
```

`--remote` es un remoto configurado por nombre. El commit y tag local deben resolver al preparado. Record consulta `git ls-remote --tags`, incluye el pelado de tags anotados y produce un plan sin escribir publicación. Un tag solo local, remoto inaccesible, tag con otro SHA o candidato/evidencia cambiados bloquean. Apply vuelve a comprobarlo antes de crear publication.json. Componentes que comparten repo/tag deben coincidir en el mismo commit. Publicar uno no publica otros pendientes; dependencias explícitas sí bloquean el ámbito afectado.

Publicación congela pertenencia, contratos, commit/tag y evidencia original. Cambios posteriores no reinterpretan la historia. Nunca editar un registro publicado para corregirlo; se necesita otra entrega/evento autorizado. Esta publicación Git no acredita salud de un entorno.

## Instalación nativa y aliases

```bash
roclec --project ROOT --json skills
roclec --project ROOT --json skills --into COMPONENT
# Solo para dependencias declaradas en el lock del consumidor:
roclec --project ROOT --json skills --restore
```

Se instalan 17 skills para Codex y Claude, launcher, guía/schema y atribución. AGENTS.md/CLAUDE.md conservan el texto del consumidor fuera de un único bloque administrado. Se siembran plantillas/constitución solo si faltan y se preservan en refreshes. Una skill propia sin marcador administrado bloquea la actualización completa. `.roclec/installation.json` registra el hash de cada archivo nativo administrado (skills `roclec-*` de ambos hosts, `workflow.md`, `model.md` y el launcher); en un refresh se borra, dentro del mismo journal recuperable, el archivo que Roclec instaló y ya no distribuye, si conserva el hash registrado. Si uno de esos archivos, retirado o vigente, fue editado, el refresh completo se rechaza con `MANAGED_FILE_EDITED` antes de escribir, listando cada ruta: restaurarla (por ejemplo `git checkout -- RUTA`) o borrarla para aceptar la versión nueva, y mover el contenido propio a un archivo del consumidor. Sin manifiesto previo rige solo la regla del marcador y no se borra nada. Plantillas, constitución, `.gitignore`, notices, link y el texto fuera del bloque de AGENTS.md/CLAUDE.md no se comparan por hash; los archivos del adaptador (`.specify/`, skills `speckit-*`, comandos) nunca se podan ni se marcan como editados, por lo que `skills` después de `speckit` los conserva. Un repo enlazado debe estar explícitamente configurado y conserva su propia instalación con link a la autoridad original. Dependencias externas solo se restauran desde skills-lock.json, sin adivinar tecnología.

### Modelo por rol

El perfil 3 acepta una tabla opcional `[agents.<rol>]` para fijar, por host, el modelo de los roles `specifier`, `implementer` y `reviewer`:

```toml
[agents.implementer]
claude = "nombre-de-modelo-del-host"
codex = "nombre-de-modelo-del-host"
```

Sin la tabla, o sin la entrada de un host, el rol hereda el modelo de la sesión del host. Roclec no valida el nombre: lo escribe en la definición generada para ese host, que lo acepta o lo rechaza al cargar el rol; para volver a heredar, se quita la entrada. Un rol inexistente, el coordinador (que corre en la sesión del usuario) o un host distinto de `claude` y `codex` se rechazan con `INVALID_INPUT` y su remedio. El contrato del rol no nombra modelos ni proveedores.

`init` sigue siendo mínimo; no importa reglas del producto ni instala automáticamente un stack. Las instrucciones instaladas son entradas potencialmente relevantes: el perfil debe clasificarlas como corresponda antes de declarar un candidato suficiente, sin ocultar cambios de implementación.

Para el adaptador opcional, inicializar antes la integración spec-kit deseada (compatible `>=0.13.4,<0.14.0`, probada con 0.13.4), y ejecutar:

```bash
roclec --project ROOT --json speckit
```

El instalador prepara los efectos de archivos del CLI spec-kit en un directorio temporal y aplica el diff validado con journal. Aliases y referencias se generan de las mismas skills nativas, sin prompts duplicados ni hooks que encadenen acciones. Package/preset/extensión comparten la versión del paquete. `assets/legacy` conserva únicamente el oráculo explícito de perfil 1; el consumidor no se auto-despacha a él.

## Recuperación y evaluación

Ante IO_PARTIAL, conservar el journal y usar `operation inspect ID` / `operation recover ID` en la raíz de esa operación. Se comprueban autoridades, candidato de código y remoto cuando corresponde; la recuperación rechaza divergencias y no revierte avances posteriores. Los locks son locales. Un fallo de restauración externa distingue instrucciones nativas ya instaladas y requiere reintentar esa restauración; no se presenta como operación completa.

[Implementación y evidencias](implementation/c3.md) registra el wheel exacto, unit tests, harness instalado, fallos inyectados e instalación Codex/Claude. Las pruebas usan remotos Git desechables y observaciones declaradas sintéticas, sin aceptación de producto ni ejecución de modelos.
