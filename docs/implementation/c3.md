## Decisión resuelta y comportamiento

El usuario eligió un RUN propio de release para el contrato final conjunto, frente a transferir runs de cada CHG. Se añadió `run verify --release VERSION --component NAME --base REF`, con identidad de ámbito release y change_id null. Reutiliza la ejecución, cobertura, logs, interrupciones y clasificación de candidatos de C2. No crea un CHG ficticio ni exige criterios sustituidos por otros miembros. El conjunto sigue el linaje explícito desde la publicación anterior, o el baseline publicado de la corrección histórica.

`releases.py` comprueba pertenencia única, aprobación exacta, integración, dependencias, versión, RUN final, cobertura/revisión e inclusión real de fixes. Fix y backport usan SHA Git completo inmutable. Un objeto inexistente, un commit fuera del candidato o backport sin preservación vigente produce FIX_NOT_INCLUDED. Preparación congela los commits resueltos y la relación con el EVD real, sin adivinar IDs futuros al aprobar.

La revisión continúa siendo opcional por CHG. El conjunto deriva una identidad de las decisiones adoptadas; un miembro participante requiere revisión favorable vigente del contrato final del componente. Ejecutar pruebas sigue permitido antes del informe. Cambiar la política vuelve obsoleto el informe correspondiente, y desactivarla conserva historia/hallazgos.

Prepare exporta un plan; apply lo reconstruye y crea una preparación inmutable por SHA. Record consulta el remoto configurado por nombre y exige commit/tag local/remoto iguales al preparado, incluyendo pelado de tags anotados. Un tag solo local o remoto distinto no acredita publicación. Apply revalida y registra publication.json; no crea tags, no hace push ni despliega. Los descendientes de metadatos con entradas idénticas no cambian el commit preparado que se registra como enviado.

Publicado congela pertenencia, contratos, candidato y evidencia. Las consultas históricas validan preparación y publicación sin consultar la red. Otras integraciones no reinterpretan los textos/AC publicados. Un componente puede publicarse mientras otro sigue pendiente, salvo dependencias explícitas. Una colisión de repo/tag con otro commit se rechaza.

`store.py` admite los dos nuevos tipos de plan y revalida candidato/remoto al recuperar. Una interrupción conserva el journal; divergencias bloquean recuperación sin borrar el registro ya escrito. Repetir apply devuelve el recibo histórico sin repetir efectos ni retroceder autoridades.

## Skills, plantillas y distribución

Se actualizaron las 17 skills canónicas, el formato de informe, guías y plantillas al modelo nativo. Ya no instruyen a usar front-matter done, transition, features NNN o amendments NNN-A1 como autoridades. Se aplicó la skill skill-creator y su validación estructural; no se ejecutó un modelo para dar por buena su interpretación.

`installation.py` instala/actualiza Codex y Claude mediante escrituras protegidas/journal. Conserva texto propio fuera del bloque administrado, principios, plantillas y dependencias del consumidor. Rechaza sobrescribir skills propias. Se puede instalar en un componente explícitamente configurado, manteniendo una autoridad de proyecto. La restauración externa requiere el lock del consumidor; su salida va a stderr para preservar el sobre JSON. El harness no restaura dependencias externas.

El adaptador genera aliases desde las mismas skills y prepara sus efectos de archivos en staging antes de aplicar el diff. Se comprobaron instalación y refresh con el CLI spec-kit real para Codex/Claude. Se conservan versión común y atribución MIT/procedencia. Los assets anteriores se copiaron byte a byte a `assets/legacy` para las regresiones explícitas; cli.legacy_main y Project usan ese oráculo, nunca un auto-dispatch del consumidor perfil 2. El runtime nativo usa Profile y las fuentes canónicas nuevas.

## Validación

El [harness final](../evaluation/evidence-inventory.md) fija huella del wheel, versión, ámbito, comandos/salidas y resultado. La [síntesis](../evaluation/evidence-inventory.md) conserva los comandos requeridos, logs, empaquetado, validación de skills y comparación de preservación. [Primer recorrido](../evaluation/evidence-inventory.md) y [recorrido de instalación](../evaluation/evidence-inventory.md) son iteraciones históricas y no certifican el wheel final por compartir su nombre.

Resultado final: **55 tests aprobados y 710/710 comprobaciones del harness**: 220 C1 nativas/empaquetado, 173 C2 nativas, 205 C3 nativas y 112 de regresión anterior. `--spec-kit` ejercitó instalación/refresh nativos en Codex y Claude. Los 18 módulos y 59 assets del wheel coinciden byte a byte con el workspace: 30 assets canónicos y 29 del snapshot histórico. Las 17 skills nativas pasaron quick_validate. Los números son aserciones de prueba, no 710 escenarios de producto ni evaluación de agentes.

Se ejecutan tests reales sobre consumidores desechables y CLI instalada, sin PYTHONPATH/PYTHONHOME. C3 construye un remoto Git bare local y publica tags de prueba con el propio harness; Roclec solo consulta/registra esa publicación. Los casos incluyen tags anotados y lightweight, tag solo local, remoto cambiado entre export/apply, metadatos posteriores al preparado, miembro pendiente, contrato histórico tras evolución, release de varios cambios con AC sustituidos, fixes inexistentes/no incluidos y backport con/sin preservación.

Las interrupciones de preparación/publicación antes del recibo dejan journal; recovery rechaza código o remoto divergentes y completa la misma operación cuando las precondiciones vuelven a coincidir. Se interrumpe también la instalación tras escribir el launcher, comprobando recuperación del bit ejecutable. La instalación/refresh preserva contenido propio y enlaces de skills ajenos. Se mantienen C1/C2 y las regresiones de perfil 1 como ámbitos distintos del informe.

Se conserva la distinción entre aserciones, escenarios y evaluación semántica. Un test con relación AC no demuestra por sí solo suficiencia; la clasificación de un fix, la independencia y la calidad visual no se autentican por JSON. Los actores/informes de prueba son declarados sintéticos. No hubo llamadas a modelos, aceptación comercial, despliegue ni uso del piloto.

## Preservación y publicación del kit

Antes de editar se respaldaron archivos versionados/no ignorados, hashes/permisos y diffs staged/unstaged fuera del repo. La síntesis enumera cambios existentes editados intencionalmente y comprueba el resto contra ese respaldo; no se reseteó, limpió, staged ni confirmó trabajo del usuario. Se conservan intactas las evidencias históricas de C1/C2. Las releases/tags/remotos de pruebas están exclusivamente en directorios temporales.

La versión de desarrollo sigue 0.8.0 porque esta tarea implementa C3 y no pide publicar el paquete. Package, preset y extensión siguen una versión común; SHA-256 distingue los wheels de desarrollo. Publicar el kit, operar el piloto y aceptar su producto requieren su propio alcance/autorización. C3 acredita el runtime y la distribución probados, sin convertir esas acciones futuras en realizadas.
